# Хранение учётных данных — спецификация дизайна

Дата: 2026-10-18. Статус: **одобрена владельцем 2026-10-18** (кода нет). Относится ко всему проекту, а не к подпроекту №4; выполняется в одном плане с ним (Task 20), но может быть принята отдельно.

Пометки: **[решено]** — слова владельца; **[моё]** — мой выбор, владелец делегировал его фразой «по всем правилам, принятым в сообществе».

## 1. Зачем

Проект станет публичным и перейдёт к другому пользователю. Пароль учётной записи ВШЭ сейчас лежит в `.env` открытым текстом, а `storage/hse-session.json` (куки и токены сессии) — не менее чувствителен. Цель: привести хранение секретов к общепринятым правилам (не коммитить секреты, предпочитать системное хранилище, ограничивать права на файлы, не писать секреты в логи, описать действия при утечке), не вводя собственной криптографии.

**[решено]** Пароль в `.env` открытым текстом — исправить «по всем правилам сообщества».

## 2. Решения

| Вопрос | Решение |
|---|---|
| Источники пароля, приоритет | **[моё]** 1) переменная окружения процесса `HSE_PASSWORD` (в том числе заданная клиентом MCP); 2) системное хранилище (Windows Credential Manager, macOS Keychain, Linux Secret Service) через `@napi-rs/keyring`, служба `hsemcp`, учётная запись — значение `HSE_EMAIL`; 3) `.env` — запасной путь. `HSE_EMAIL` берётся из окружения или `.env` (это не секрет) |
| Зависимость | **[моё]** `@napi-rs/keyring` (MIT, v2.1.1 на 2026-10-10, готовые бинарники без компиляции) как `optionalDependencies`; подключается динамическим `import()` с перехватом ошибки. Нет пакета или хранилище недоступно — тихий переход к `.env` с предупреждением, установка не падает |
| Linux | **[моё]** без Secret Service пакет молча уходит в хранилище ядра `keyutils`, которое не переживает перезагрузку; поэтому на Linux запись создаётся с `{ linux: { store: "secret-service" } }`, при его отсутствии хранилище считается недоступным |
| Команды | **[моё]** `npm run credentials:set` (запрашивает пароль без эха, пишет в хранилище; email — из окружения/`.env` или запрос), `credentials:clear` (удаляет запись), `credentials:status` (печатает **только** источник: `env`/`keychain`/`dotenv`/`none`, без значений и без email) |
| `.env` как запасной путь | **[моё]** остаётся, при чтении пароля из него — одно предупреждение в stderr («пароль взят из .env; безопаснее: npm run credentials:set») без значения; на POSIX при правах, допускающих группу/остальных (`mode & 0o077`), — отдельное предупреждение; на Windows проверка прав не выполняется (нет надёжного способа без внешних средств), в README — команда `icacls` |
| Файлы-секреты | **[моё]** `storage/hse-session.json` и `storage/writes/key` создаются с `0o600` (POSIX); на Windows — best-effort `icacls <файл> /grant:r <ДОМЕН\пользователь>:(F) /inheritance:r` (сначала выдача права, потом снятие наследования; без домена — имя пользователя) в `try/catch`, без сообщений об ошибке с путями. Помощники `restrictFile(path)` и `restrictDir(path)`. Каталоги `storage/` и `storage/writes/` ограничиваются один раз за процесс (POSIX `0o700`; Windows `(OI)(CI)(F)` с наследованием), чтобы новые файлы создавались сразу с ограниченными правами, без окна между записью и `restrictFile`. Уже существующий ключ на Windows ограничивается при чтении (раз за процесс) |
| Отключение хранилища | **[моё]** `HSE_DISABLE_KEYCHAIN=true` отключает системное хранилище целиком (CI, серверы без графической сессии, Linux без Secret Service: проба Secret Service при старте — синхронный вызов без таймаута). `npm test` задаёт её сам, чтобы тесты не трогали настоящее хранилище |
| Логи и ошибки | **[моё]** значение пароля, куки и токены не попадают в ошибки, stderr и ответы тулов (правило уже действует, проверяется скриптом) |
| Репозиторий | **[моё]** `.env`, `storage/` — в `.gitignore` (уже); `.env.example` без значений с пометкой про хранилище; новый `SECURITY.md` (как сообщить об уязвимости; что делать при утечке: сменить пароль ВШЭ, удалить `storage/hse-session.json` и `storage/writes/key` (папка `storage/outbox/` и журнал записей — данные пользователя, их не трогать), `npm run credentials:clear`); в README — рекомендация включить secret scanning и push protection на GitHub и, по желанию, `gitleaks` в pre-commit (в зависимости проекта не добавляется) |
| Модель угроз | **[моё]** защита от случайной утечки (коммит, скриншот, лог, публикация репозитория) и от чтения файла другим пользователем ОС; не защита от вредоносной программы под тем же пользователем: пароль всё равно вводится в форму Keycloak и находится в памяти процесса |

## 3. Не-цели

Собственное шифрование `.env` (иллюзия защиты при ключе рядом), серверные менеджеры секретов, пароли приложений вместо SSO (их у ВШЭ нет), двухфакторная аутентификация (MAX — вне проекта).

## 4. Проверка

Постоянный тест `test/credentials.test.mjs` (`node:test`, `npm test`; без сети и без реального хранилища, подставной `KeyStore`): приоритет env → хранилище → `.env`; хранилище `null` → откат на `.env`; источник сообщается верно; предупреждение и вывод `status` не содержат значения пароля и email; `restrictFile` на POSIX даёт `0o600` (на Windows — `t.skip()`). Живая проверка — только с владельцем и с его разрешением: `credentials:set` → вход через `hsemcp` без `HSE_PASSWORD` в `.env` → `credentials:status` показывает `keychain` → `credentials:clear` (запись и удаление затрагивают Credential Manager владельца).

## 5. Допущения (не проверено)

Поведение `@napi-rs/keyring` на Windows при заблокированном хранилище и на Linux без графической сессии; ограничение размера пароля; `icacls` на нестандартных профилях Windows.
