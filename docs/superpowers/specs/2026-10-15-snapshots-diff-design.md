# Подпроект №3 «Проактивность: снапшоты и diff» — спецификация дизайна

Дата: 2026-10-15. Статус: **дизайн утверждён; прошёл ревью `opus` (§17) и живую проверку допущений
на одном аккаунте за один день (§18); реализация не начата**. База: ветка `snapshots-diff` от
`origin/reliability-rework` (PR №1 ещё открыт; после его слияния ветка переносится на `master`).
Подпроект 2 «Сводки» (`digest`) уже в базе. Ревью дало 2 блокирующих и 9 существенных замечаний; все
учтены в этой версии.

**Три решения приняты ПО УМОЛЧАНИЮ — пользователь по ним не отвечал, их можно оспорить на ревью
спеки:** (1) заголовки входящего (темы писем, заголовки уведомлений) хранятся как есть — принятый
риск (§7); (2) оценки разбираются новым парсером `extractGradeTable`, а при неподходящей вёрстке
область возвращает `unsupported` (§5, п. 6); (3) защита от параллельных процессов — lock-файл (§7).

## 1. Цель

Вместо «что есть сейчас» (`digest`) отвечать на «что изменилось с прошлого раза»: новые и
изменённые дедлайны и задания, изменения расписания, новое входящее и смена статусов заявок, новые
оценки. Часть цели верхнего уровня «управлять учебной жизнью через MCP» (подпроект 3 из 4; №4 —
записывающие действия — сюда не входит).

| Вопрос | Решение |

## 3. Подходы

- A. Только последний снимок на область. Отклонён: событие теряется, как только база сдвинулась и
  ответ не дошёл; «за неделю» невозможно.
- **B. Последняя база по источнику + журнал событий с курсором. Выбран.**
- C. Только хэши фактов. Отклонён: «было 7, стало 8» и «срок сдвинулся с X на Y» невозможны.

## 5. Модель фактов

Факт: `{ id, scope, kind, title, course?, attrs }`. `id` стабилен между снимками, в `attrs` только
отслеживаемые поля. Не входят в факт: `updated`, время получения, url с query, `raw`, `actionable`,
порядок, свободный текст. Сравниваются только `attrs`, в каноническом виде (§6).

Источник → факты; **единица базы — источник** (`lms_calendar`, `elk_windows`, `elk_schedule`,
`lms_messages`, `elk_notifications`, `elk_claims`, `lms_grades:<courseId>`).

| Область | Источник | `id` | `attrs` | События |
|---|---|---|---|---|
| `deadlines` | `lms.listActionEvents(today−180д … endOfDay(today+60д))` | id события Moodle | срок (`due`), название | `added`, `changed(due)`, `removed`, `overdue` |
| `deadlines` | `elk.getCourseEvaluationStatus` (окна СОП) | период | срок окончания, статус | `added`, `changed`, `removed` |
| `schedule` | `elk.getSchedule(today … today+14д)` | `дата\|начало\|название\|тип` | конец, аудитория, корпус | `added`, `changed`, `removed`, `moved` |
| `inbox` | `lms.listMessages(200)` | id сообщения | заголовок | только `added` |
| `inbox` | `elk.getNotifications(100)` | id уведомления | заголовок | только `added` |
| `claims` | `elk.listRequests(500)` | `num` | `stateName`, `active` | `added`, `changed` |
| `grades` | `lms.listGradeItems(courseId)` (новый ресурс, §5 п. 6) по актуальным курсам | `courseId\|путь категорий\|название элемента` | оценка (текст ячейки) | `added` (только с непустой оценкой), `changed` |

Правила:

1. **«Пропало из календаря» ≠ «сдано».** Календарь не показывает сданное, но так же исчезает
   завершённое без сдачи, удалённое и вышедшее за окно. Событие `removed` формулируется как
   «пропало из календаря».
2. **`overdue` не входит в `attrs`.** В Moodle `overdue = timesort < now` — это ход часов, а не
   изменение данных. Событие `overdue` порождается, когда `baseline.takenAt < due ≤ now`, а элемент
   всё ещё в календаре. Оно помечено `cause: "clock"`.
3. **Прочтение — не событие.** В `inbox` порождаются только `added`; пропажа письма/уведомления
   из выборки `removed` не даёт.
4. **Покрытие (`coverage`) у каждого источника, имеющего скользящее окно** — см. §11. `added` и
   `removed` считаются только для фактов, чьё значение оси лежит в пересечении старого и нового покрытий.
5. **Расписание.** `id` включает начало, поэтому перенос выглядит как `removed` + `added`. После
   diff — проход, который склеивает пару с одинаковыми (название, тип) внутри пересечения покрытий в
   одно событие `moved` (`from`/`to`: дата, начало, аудитория). Неоднозначная склейка (несколько
   кандидатов) не выполняется. Сдвоенные пары и подгруппы различаются началом в `id`.
   **Подтверждено вживую (§18):** `lesson_number` есть в ответе, но `null` у всех 20 занятий — для
   ключа непригоден; полей отмены, статуса и id занятия нет (есть `lesson_type_id` — число и
   `parent_schedule` — строка, смысл не установлен). Ключ `дата|начало|название|тип` дал 0 коллизий;
   ключ без начала (`дата|название|тип`) — 3 коллизии на 20 занятиях, то есть начало в `id`
   необходимо. Отмену пары по полям отличить нельзя: отмена = `removed`.
6. **Оценки.** Существующий `extractTable` непригоден: имя элемента Moodle рендерит в `<th>`
   (`column-itemname`), а `extractTable` читает только `td` и сопоставляет их с `thead th` по индексу.
   **Подтверждено вживую на 5 курсах (§18):** `table.user-grade` есть везде; имя — `th.column-itemname`
   с уровнем `levelN` (до `level2`); колонки по классам — `column-weight`, `column-grade`,
   `column-range`, `column-percentage`, `column-feedback`, `column-contributiontocoursetotal`;
   ячеек `leader` с `rowspan` на этой теме нет; коллизий ключа «путь/имя» 0; много оценок «-».
   **Живое подтверждение дефекта `extractTable`:** у строк 6 `td` сопоставляются с 7 заголовками
   `thead th` по индексу, поэтому ключи сдвинуты на одну позицию (в «название элемента» попадает вес),
   имя элемента (в `th`) теряется, седьмая колонка не получает ключа. Следствие: нужен
   `extractGradeTable` — имя из `th.column-itemname`, путь категорий из `levelN`, колонки по классам,
   не по индексу; и он живёт в **новом** ресурсе `lms.grade-items`. Существующие `lms.getGrades` и тул
   `lms_get_grades` в №3 не меняются; их дефект — отдельный пункт «чинится отдельно» (§14).
   В `attrs` кладётся **только** оценка: «Процент» и «Вклад» пересчитываются каскадом от любой оценки.
   Новый элемент с пустой оценкой («-») база запоминает, но событием не считает (подтверждено вживую:
   «-» — частый случай). Если разбор не нашёл колонки, источник получает статус
   `error: "unsupported grade table"`, а не ложные события.

## 6. Нормализация

- Строки: Unicode NFC, `trim`, схлопывание пробельных символов, регистр не меняется.
- **Моменты — без участия часового пояса машины.** Moodle (unix-секунды) → `YYYY-MM-DDTHH:mmZ` в
  UTC. ЕЛК и СОП (локальные строки даты и времени МСК) хранятся как наивное МСК-время
  `YYYY-MM-DDTHH:mm`, без перевода через `Date` и без смещения. Сравниваются строки. Поэтому смена пояса ОС
  не порождает массовых `changed`. (МСК без перехода на летнее время с 2014 г.; риск только от пояса
  машины.) Это отличается от `toLocalIso` в `digest`, который пишет смещение машины.
- Отпечаток `attrs`: JSON с отсортированными ключами; `null`, `undefined` и пустая строка равны.
- Данные из кэша заморожены (`Object.freeze`): нормализация копирует, а не мутирует.

## 7. Хранение

Один файл `storage/changes/state.json` (каталог `storage/` уже в `.gitignore`). Путь вычисляется от
расположения модуля, а не от `cwd` (как `config.ts`), через общий хелпер `projectRoot` (§4): сейчас
он вычисляется отдельно в `config.ts:8` и `browser-session.ts:13` и не экспортируется, третья копия
в `store.ts` не заводится. Пишется целиком (порядка 100–300 КБ).

```
{ version, rev, nextSeq, issued: { [scope]: seq }, lost: { [scope]: n },
  baselines: { [source]: { takenAt, coverage?: {from,to}, facts: { [id]: Fact } } },
  journal:   [ { seq, at, scope, source, type, cause?, id, kind, title, course?, fields?: [...] } ],
  seen:      { [scope]: seq },
  issues?:   { [ackSeq]: Scope[] } }
```

**Не пишется никогда:** токены и всё из `storageState`, email, ФИО (`sender`, `executorFio`,
`createdBy*`), тела писем, текст уведомлений и заявок (у заявки `title` = только `service`), url с query,
`raw`. Названия курсов, оценок, темы писем и заголовки уведомлений остаются — без них diff не читается;
тема письма может содержать ФИО, это **принятый риск**, локальный файл, сброс — `hse_changes_reset`.

**Нумерация.** `seq` глобален по всем областям и выдаётся `nextSeq++` только при успешном коммите
(событие без записи не получает `seq`). `nextSeq` монотонен: не сбрасывается ни срезом журнала, ни
`hse_changes_reset`. После `.corrupt` нумерация может начаться заново **вместе** со сбросом `seen`.
`issued[scope]` — наибольший `seq` области, выданный в ответе (ограничивает `ack`, §10). `issues` —
области ответов по их `ackSeq`, последние 50 записей (`ack` подтверждает только области того ответа, §10);
поле необязательное, файлы без него читаются, версия формата не меняется.

**Срок жизни.**
- Журнал: событие старше 30 дней срезается **только если его `seq` ≤ min(`seen`)** по областям;
  жёсткий потолок 500 событий срезает старейшие, в том числе невыданные. Срезанное невыданное
  учитывается в `lost[scope]`; ответ сообщает `gap` (§10).
- Базы: перезаписываются. База `lms_grades:<id>`, не обновлявшаяся 90 дней (курс исчез из актуальных),
  удаляется.
- Очистка: `hse_changes_reset`, либо удаление файла (штатный «первый запуск»).

**Права.** Создаётся с `0o600`, но на Windows (платформа проекта) `mode` управляет только флагом
записи, разграничения owner/group/others нет: реальная защита — ACL профиля пользователя, как у
`storage/hse-session.json`, который чувствительнее. Больше не обещается.

**Целостность и отказы ввода-вывода.**
- `.corrupt` — **только** при `JSON.parse` или схеме, не прошедших проверку; имя с меткой времени, прежние
  `.corrupt` не затираются.
- Ошибка чтения/переименования (`EPERM`/`EACCES`/`EBUSY` из-за антивируса, индексатора, другого
  процесса) — повторы с короткой паузой (≈5 попыток), затем `persisted: false` без записи и без
  `.corrupt`.
- `version` новее известной (откат на старый код) — файл не трогается, ответ `error`, `persisted: false`.
- При `io-error` чтения и `version` новее — коммита нет; статусы областей `error`, предупреждение в
  `warnings`, `persisted: false`. Если `version` новее уже при первом чтении (до сбора), источники не
  опрашиваются: запись заведомо будет пропущена.
- Запись: во временный файл с `process.pid` и `rename` (как `saveStorageState`), повторы для `rename`.
- Параллельные процессы (два хоста): lock-файл `state.json.lock` через `fs.openSync(..., "wx")`
  только на цикл «прочитать → пересчитать diff от свежей базы → записать»; сбор данных идёт вне
  блокировки; устаревшая блокировка (> 30 с) снимается. Внутри процесса — мьютекс. Проверка `rev`
  сохраняется как дополнительная. Блокировка не получена за 10 с — ответ как при ошибке записи
  (`persisted: false`, предупреждение), без исключения.
- Устаревший снимок: если под блокировкой база источника новее снимка этого вызова (`takenAt` базы
  больше — параллельный вызов снял позже, а закоммитил раньше), база не трогается, событий нет,
  источник получает `skipped: "снимок устарел: база новее"`. Иначе diff старого снимка от новой базы дал
  бы ложные `changed` туда и обратно и откатил бы `takenAt` (повторный `overdue`).

## 8. Свежесть кэша

`clearCache` перед снимком отвергнут: `generation` общий на весь кэш, поэтому любой сброс запрещает
запись всем идущим загрузкам во всех доменах и убирает in-flight-дедупликацию. Вместо этого —
требование свежести на уровне вызова.

- `ResourceCallOptions.maxAgeMs?`. `Entry.storedAt` — **момент старта** загрузки. Запись кэша годна,
  если `expiresAt > now` и `now − storedAt ≤ maxAgeMs`. In-flight принимается, только если стартовал не
  раньше `now − maxAgeMs`; иначе запускается новая загрузка и становится актуальной для ключа.
  Запись в хранилище разрешена, только если `startedAt ≥ storedAt` текущей записи — старая загрузка,
  завершившаяся позже, не затирает свежую.
- Дефолт снимка — `maxAgeMs = 60 с` (сразу после `my_today` страницы не открываются повторно);
  `fresh: true` → `0`. `maxAgeMs: 0` — «перечитай и сохрани», а не «не кэшируй».
- Восемь функций: `elk.getSchedule` (сама ресурсом не является — передаёт `opts` в **каждый**
  недельный вызов `elkScheduleWeek`; если забыть, ошибки не будет, свежесть молча не применится — §15),
  `getNotifications`, `listRequests`, `getCourseEvaluationStatus`; `lms.listActionEvents`, `listMessages`,
  `listCourses` и новый `listGradeItems` (ресурс оценок; существующий `getGrades` не меняется).
- Полнота: ключи кэша от `limit` не зависят, загрузка всегда берёт максимум, `limit` режет выдачу —
  снимок вызывает с максимумом (`getNotifications(100)`, `listMessages(200)`, `listRequests(500)`).
- `hse_changes` не вызывает `clearCache`.

## 9. Лимитер и бюджет оценок

Снимок не обходит лимитер (3 страницы, ≥300 мс) и не держит вложенных `withPage`. Дедлайн ресурса 45 с
**включает ожидание слота лимитера**, поэтому запускать все курсы оценок через `Promise.all` нельзя:
хвост очереди упал бы со статусом `error` по таймауту.

- `grades`: пул ≤ 3 одновременных загрузок; новые курсы не запускаются, когда бюджета области (90 с)
  не хватает; незапущенные получают `skipped`, их базы прежние.
- Порядок обхода — по давности последнего снимка курса (самые старые первыми), чтобы один и тот же
  хвост не пропускался вечно.
- Только актуальные курсы (`selectCourses`); фильтр `courses` ограничивает набор.
- Прочие области: источник ограничен дедлайном ресурса и таймаутом `runSource` (40 с).
- **Замер живой проверки (§18; один аккаунт, один день, 19 актуальных курсов).** Холодный процесс:
  всего 59,3 с и 24 страницы — `listCourses` 7,3 с; `listActionEvents` 3,8 с; `getNotifications`
  13,1 с (первая загрузка ЕЛК, токен получается через страницу); СОП 3,5 с; `listMessages` 1,3 с;
  `getSchedule` на 14 дней 0,35 с без страницы; `listRequests` 0,09 с без страницы; оценки пулом 3 —
  30,0 с, 19 страниц, по курсу 1,4–8,9 с. «Тёплый» (кэш сброшен, браузер и сессия живы): 35,8 с и 23
  страницы (оценки 26,4 с, один курс 24 с — выброс). Повтор из кэша: 0 мс и 0 страниц.
  Выводы: бюджет `grades` 90 с достаточен на этом аккаунте; полный холодный снимок с оценками (≈ 59 с)
  вплотную к таймауту запроса SDK 60 с, что подтверждает необходимость `ack` (§10, Б1); набор областей по
  умолчанию (без `grades`) ≈ 29 с холодным (сумма замеров без оценок, включая `listCourses`, который
  областям по умолчанию не нужен). Выборка — один аккаунт и один день; на аккаунте с другим числом
  курсов цифры иные.

Страницы по областям: `deadlines` 2 (календарь + СОП), `inbox` 1 (LMS-сообщения; уведомления ЕЛК —
прямой API), `claims`/`schedule` 0 (прямой API; холодному процессу нужна 1 страница на токен),
`grades` 1 (`listCourses`) + N курсов.

## 10. Интерфейс

### `hse_changes`

| Параметр | Значение |
|---|---|
| `scopes?` | подмножество `deadlines`, `schedule`, `inbox`, `claims`, `grades`; по умолчанию все **кроме** `grades` |
| `courses?` | фильтр для `grades` (число — id, строка — подстрока названия) |
| `fresh?` | `true` → `maxAgeMs: 0`; по умолчанию 60 с |
| `since?` | `"7d"` или ISO: вернуть журнал за период; сам `since` `seen` не меняет (переданный вместе с ним `ack` действует как обычно, независимо от `since`); снимок и коммит выполняются как обычно; `ackSeq: null`, `issued` и `issues` не меняются |
| `ack?` | `ackSeq` **полученного** ответа; сдвигает `seen` только для областей того ответа (`issues[ack]`), входящих в вызов, не выше выданного по области (`issued[scope]`) |

Порядок: (1) снять факты источников (вне блокировки); (2) под lock-файлом перечитать базу; (3) если есть
`ack` — применить его к `seen` (правило ниже), пересчитать diff от свежей базы и **одним коммитом**
записать базы, события и курсор; (4) вернуть события с `seq > seen[scope]`. **Курсор двигается только
`ack` предыдущей выдачи, в этом же вызове он не двигается**: событие не теряется, даже если ответ не
дошёл (таймаут SDK 60 с, остановка фоновой задачи). Неподтверждённое возвращается снова — дубль
допустим, потеря нет. `extra.signal` останавливает незапущенную работу (курсы, источники) и пропускает
шаг коммита, если отмена пришла до него (в том числе во время ожидания блокировки); для корректности он
не нужен, а для того, чтобы не тратить слоты лимитера и не писать после отмены.

Выдача упорядочена по `seq` по всем областям сразу; потолок 200 событий срезает **префикс** (поэтому
`ack = ackSeq` никогда не «перепрыгивает» невыданное); `omitted` — сколько осталось. `issued` — карта
`{ [scope]: seq }`: наибольший `seq`, возвращённый в ответе по области; записывается тем же коммитом
(шаг 3), ограничивает `ack` по области; `since` и `persisted: false` его не меняют. Тем же коммитом
пишется `issues[ackSeq]` — области вызова, выдавшего ответ с этим `ackSeq` (последние 50; если тот же
`ackSeq` выдан повторно, хранится пересечение областей: клиент мог получить любой из двух ответов).

Применение `ack`: `ack`, больший наибольшего когда-либо выданного `seq` (`max(issued[*])` по всем
областям), или без записи `issues[ack]` (неизвестный или вытесненный) игнорируется целиком с
предупреждением (в нём только числа). Иначе для каждой области вызова, входящей в `issues[ack]`,
`seen[scope] = max(seen[scope], min(ack, issued[scope]))`; прочие области не затрагиваются. Ответ с
`ackSeq` содержал все неподтверждённые события своих областей с `seq ≤ ackSeq`, поэтому подтверждение
только его областей ничего не теряет; `ackSeq` ответа по одной области не подтверждает события другой,
выданные в ответе, который не дошёл.

Ответ:

```json
{
  "takenAt": "…",
  "scopes":  { "deadlines": { "status": "ok|baseline|partial|error", "facts": 42, "warnings": [] } },
  "sources": { "lms_calendar": { "status": "ok|error|skipped", "ms": 2800, "error": "…" } },
  "changes": [ { "seq": 17, "at": "…", "scope": "deadlines", "type": "changed",
                 "kind": "assignment", "title": "…", "course": "…",
                 "fields": [ { "field": "due", "from": "…", "to": "…" } ] } ],
  "ackSeq": 17, "omitted": 0, "gap": { "lostEvents": 0 }, "persisted": true,
  "warnings": []
}
```

Источник `lms_courses` (список курсов) входит в область `grades` и виден в `sources`; его отказ даёт
статус области `error`. `warnings: string[]` — предупреждения вызова, не относящиеся к одному источнику
(проигнорированный `ack`, повреждённый или недоступный `state.json`, ошибка записи или блокировки, отмена), без
названий, ФИО и query-строк.

`ackSeq` — значение, которое следующий вызов передаёт в `ack`. Если подтверждения не будет, события
повторятся; в описании тула это сказано явно. **Первый запуск считается по источнику:** нет базы
источника → база создаётся без событий, статус `baseline`. Новый курс в `grades` и источник, упавший при
первом запуске, получают базу позже тем же правилом, поэтому ложных `added` нет.

### `hse_changes_reset({ scope?, confirm: true })`

Стирает базы и события области (или всего). Без `confirm: true` — отказ. `nextSeq` не сбрасывается;
`seen` ставится в `nextSeq − 1`.

### Ошибки записи

Ошибка записи на диск: события возвращаются, `persisted: false`, базы, `seen` и `nextSeq` не меняются,
следующий вызов вычислит то же самое. Тул не бросает исключений: отказ источника — статус в `sources`,
по образцу `digest`.

Описания тулов явно разводят `digest` («что есть») и `hse_changes` («что изменилось»).

## 11. Ложные события и частичные отказы

Источник → правила:

1. **Покрытие.** `lms_calendar`: ось — `due`; `from = today − 180 д`, `to = endOfDay(today + 60 д)`
   (последний день целиком: клиент отбрасывает события `due > to`, и полночь потеряла бы последний день),
   где `today` — полночь, а не `now`: те же даты, от которых строится ключ кэша (`lms/client.ts:224`), иначе
   покрытие и загрузка разойдутся; `coverage.to` — тот же момент в UTC; при `truncated` `to` — минута
   перед `max(due)` загруженного (усечение отрезает самые поздние события, граница плавает; событие с тем
   же сроком могло быть отрезано границей страницы и не должно стать ложным `added`).
   `elk_schedule`: `from = today`, `to = today + 14 д`. `inbox`: `from = min(time)` выборки, если вернулось
   ровно `limit`, иначе без нижней границы. `added`/`removed` — только внутри пересечения покрытий; факты
   вне пересечения не порождают событий и сохраняются как есть, пока не окажутся в покрытии.
2. **Усечённый календарь** → `removed` по `lms_calendar` не вычисляется, `warnings`.
3. **Отказ источника** → база прежняя, событий нет, статус `error`; остальные источники коммитятся
   независимо. RUZ как замена ЕЛК-расписания **не используется** (другие `id` и формат — ложные
   события).
4. **Новые («`added`») во входящем** — только элементы свежее самого старого в старой выборке (внутри
   покрытия). **Живая проверка (§18):** id сообщений (5) и уведомлений (2) монотонны относительно
   времени, порядок выдачи API убывающий и по времени, и по id, порядок стабилен между вызовами —
   но выборка крошечная, поэтому на max id всё равно не полагаемся. Даты уведомлений приходят **без
   времени** (формат `ГГГГ-ММ-ДД`), поэтому гранулярность покрытия «по времени» у уведомлений — сутки:
   «свежее самого старого» сравнивается по дате, и новое уведомление того же дня, что и самое старое в
   старой выборке, по времени не отличить: такое уведомление считается новым только по отсутствию
   его `id` в базе, а выборка усечённой по лимиту быть не должна (иначе применяется правило
   покрытия из п. 1).
5. **Календарь и override-события Moodle.** Живая проверка (7 событий: `assign` `due` ×3, `quiz`
   `close` ×4): `timesort` равен `timestart` у всех; `overdue` совпал с `timesort < now` без
   исключений; id и порядок стабильны между двумя вызовами; `truncated=false`; `courseId=null` — 0;
   `groupid` у всех 0, `userid` у всех заполнен (override-событий по группе не наблюдалось). Поле
   `eventtype` (`due`/`close`) доступно и может войти в `attrs`. **Не проверено и не проверяемо без
   записи:** сохраняется ли id события при сдвиге срока; override-события могут выглядеть как
   `removed` + `added`.
6. **Идемпотентность.** Повторный вызов сразу после первого возвращает неподтверждённое (если `ack`
   не передан) либо пусто; новых страниц нет (кэш ≤ 60 с).

## 12. istudy, RUZ и известные ограничения

- **istudy вне №3 по недостижимости.** Живая разведка 2026-10-15 (один аккаунт, один день, одно
  подключение с существующей сессией) установила:
  1. **Вход (SSO) проходит без MAX.** Цепочка по SSO-ссылке с профиля: `lk.hse.ru/profile` →
     `istudy.hse.ru/auth` → `/token` → `/dashboard`; экрана входа и поля пароля нет, упоминаний MAX и QR
     в тексте страницы нет, ответы API 200: `/api/sso/auth`, `/api/user`, `/api/user/active-role`,
     `/api/student/profiles`, `/api/student/profile`.
  2. **API профиля переехал:** `GET /api/student/<id>/profile` → `POST /api/student/profile?studentId=<id>`
     (плюс `GET /api/student/profiles`, `POST /api/user/active-role?role=…`, `GET /api/user`). Регулярка
     клиента (`istudy/client.ts:110`, `/api/student/\d+/…`) больше не совпадает; `report-info`, `rating`,
     `exams-by-period` за время ожидания (`networkidle` + 2 с) на `/dashboard` не запрашивались вообще.
  3. **Данные зачётки закрыты двухфакторным подтверждением.** Клик по разделу меню «Зачетная книжка»
     вызывает `GET /api/auth/two-factor/required` → **HTTP 412** (поля `status`, `error`, `message`,
     `details`); страница остаётся на `/dashboard`, данных зачётки нет. Это согласуется с пресс-релизом
     НИУ ВШЭ (2026-09-28; копия на spb.hse.ru от 2026-09-29): «ЯУчусь» переведена на авторизацию через
     MAX с 2FA. Что «ЯУчусь» — именно `istudy.hse.ru`, прямого источника нет (совпадают функции:
     зачётка, оценки, рейтинг).
  4. **Не установлено:** текст `message` в ответе 412 (в разведке сохранялись только типы значений);
     сохраняется ли подтверждение 2FA и на какой срок; можно ли пройти его в headless без телефона
     (вероятно, нет); какие эндпоинты отдают рейтинг, экзамены и зачётку после подтверждения.
- **Причина F9 — двойная:** смена путей API SPA (клиент перестал находить ответы) **и** 2FA-барьер
  данных зачётки. Формулировка «F9 вызван переходом входа на MAX» неточна: входу MAX не нужен, нужен
  доступу к данным. Вывод по одному прогону одного аккаунта.
- **Решение пользователя:** «MAX у меня нет и юзать я его не собираюсь». Следствие: данные зачётки
  (итоговые и экзаменационные оценки, рейтинг) для проекта недостижимы, и istudy остаётся вне №3 — это
  не вопрос объёма, а недостижимость, пока у пользователя нет MAX. Пересматривать решение не нужно.
- **Оценки — только журнал LMS** (в рамках №3). Итоговые и экзаменационные оценки из istudy не попадают.
- Точка расширения: источник — `{ id, scope, fetch → { facts, coverage, warnings } }`; источник istudy
  добавлялся бы одним извлекателем, но потребует рабочего интерактивного 2FA через MAX; **не
  планируется.**
- **Риск (не подтверждён):** двухфакторное подтверждение через MAX для LMS/ЕЛК в нашем прогоне не
  наблюдалось; если оно появится, `storage/hse-session.json` перестанет обновляться и все источники
  получат `error` — дизайн к этому устойчив (база не трогается).
- **Единого вызова «оценки всех курсов» нет:** `gradereport_overview_get_course_grades` не помечена
  `ajax: true` и отдаёт только итоговые оценки (стандартный Moodle; кастомизация ВШЭ не проверялась).
  Оценки идут постраничным обходом курсов (§9).
- RUZ доступен только из сети ВШЭ и в снимках не используется.
- MCP-сервер живёт только пока открыт хост; фонового режима вне хоста нет. Это следствие решения
  «по запросу».
