# hsemcp — Прогресс

Снимок состояния на 2026-10-14. Формат каждого пункта: что сделано → как проверено. Подробная
техническая разведка (эндпоинты, находки, тупики) — в `ROADMAP.md`, здесь только статус.

**Итого: 37 тулов в 5 сервисах данных (RUZ, SmartLMS, ЕЛК, istudy, почта) + служебный
`hse_clear_cache` + 3 агрегатора (`my_today`/`my_week`/`my_deadlines`), все read-only** — ни одной записывающей операции ни в v1, ни в доработках после
него (см. «Требования к безопасности» в `REQUIREMENTS.md`, почему это осознанное решение, а не
недоделка).

## Дорожная карта «управление учебной жизнью через MCP»

Цель верхнего уровня разложена на четыре подпроекта (каждый — свой цикл спецификация → реализация):

1. **Надёжность и скорость** — реализовано, ядро (прямые запросы ЕЛК, токен) проверено вживую
2. **Сводки и планирование** (`my_today`/`my_week`/`my_deadlines`) — реализовано, проверено вживую на одном аккаунте за один день (список — ниже)
3. Проактивность (снапшоты состояния и diff: новые оценки/задания/письма/смена расписания) — не начато
4. Действия (write): слой `confirm: true` + dry-run, затем сдача заданий/справки/заявки — не начато

### Подпроект 1: надёжность и скорость (реализовано, ядро проверено вживую)

- `src/services/elk/client.ts#fetchElkApi`: токен ЕЛК берётся один раз через `/profile` и
  кэшируется до истечения (`exp` из JWT, запас 30 с; не-JWT — 60 с), дальше JSON-API ЕЛК
  вызывается напрямую через `context.request` без открытия страницы. Параллельные вызовы делят одно
  получение токена. 401/403/не-JSON → сброс токена и один повтор; если и это не помогло, а старый
  путь «fetch внутри страницы» работает — прямые запросы отключаются на остаток жизни процесса
  (`directApiBroken`), чтобы не ломать тулы из-за отличий вне-браузерного запроса.
- `src/limiter.ts`: не больше 3 одновременно открытых страниц и ≥300 мс между открытиями
  (`openAuthenticatedPage`); слот освобождается по закрытию страницы или ошибке открытия.
- `src/cache.ts`: in-memory кэш результатов с TTL (2/5/30 мин по смыслу данных), дедупликация
  параллельных вызовов, ошибки не кэшируются, лимит 200 записей. Кэшируются `elk_*` (кроме
  `elk_open_page`), `lms_*` (кроме `lms_open_page`) и `istudy_*`; почта и RUZ — нет.
- `hse_clear_cache({ scope? })` — сброс кэша целиком или по сервису (`elk`/`lms`/`istudy`). Вместо
  параметра `refresh` в каждом туле: то же поведение без правки 33 схем.

**Проверено**: `npm run build` чистый; изолированные скрипты через `dist/` — TTL и дедупликация
кэша, ошибки не кэшируются, сброс по префиксу, результат вызова, начатого до `clearCache`, не
пишется в кэш, вытеснение при переполнении; лимитер держит потолок 3 (6 задач по 1,5 с стартуют
в +0/+308/+600/+1515/+1824/+2118 мс) и идемпотентно освобождает слоты; разбор JWT `exp`
(валидный, не-JWT, нет `exp`, мусор, нечисловой `exp`).

**Проверено вживую на реальном аккаунте (2026-10-14)**:
- `context.request` + `Authorization: Bearer` возвращает **тот же JSON**, что fetch внутри
  страницы (`/api/get-user`, `/api/get-academic-data`: оба 200, `application/json`, тела совпали
  побайтно) — гипотеза о прямых запросах без страницы подтверждена, `directApiBroken` не
  срабатывал.
- `access_token` — JWT с `exp`, время жизни **24 часа** (86400 с). Фолбэк «60 с» для не-JWT на
  практике не нужен, токен кэшируется почти на сутки.
- Плохой/пустой токен → **401 без тела** (не 200 с HTML-редиректом) — ветка «сбросить токен и
  повторить» срабатывает по статусу.
- Время вызова (холодный старт включая логин ≈ 2,8 с): прежний путь «страница на каждый вызов»
  ≈ 0,6 с на вызов; новый — первый вызов ≈ 0,5 с (включает получение токена), следующие
  вызовы других эндпоинтов 28–112 мс, повтор того же вызова из кэша результата ≈ 0 мс; 6
  разных эндпоинтов параллельно — 139 мс суммарно. То есть выигрыш ≈ 5–20× на повторных вызовах,
  а не «с секунд до миллисекунд»: прежний путь был быстрее, чем предполагалось при проектировании.

**Не проверено**: сквозной сценарий повтора при реально протухшем токене (проверен только сам
ответ API на плохой токен, не цепочка invalidate → reacquire внутри `fetchElkApi`); поведение при
протухшей SSO-сессии Keycloak; лимитер не сверялся с реальными порогами антибот-защиты ВШЭ.

**Закрыто подпроектом 2**: `lms_*` через кэш проверены вживую (повторные `listCourses`/
`listActionEvents` отдаются из кэша за ≈ 0 мс); `istudy_*` через кэш отдельно не проверялись.

### Подпроект 2: сводки и планирование (реализовано, проверено вживую на одном аккаунте)

Спецификация — `docs/superpowers/specs/2026-10-14-summaries-planning-design.md`.

- Сервис `src/services/digest/` (`types.ts`, `parse.ts`, `sources.ts`, `client.ts`, `tools.ts`),
  3 тула: `my_today`, `my_week`, `my_deadlines({ days?, courses? })`. Агрегаторы вызывают клиентские
  функции сервисов (не MCP-тулы); существующий код сервисов не менялся, кроме нового
  `lms.listActionEvents` и переноса AJAX-вызовов Moodle на лёгкую страницу (см. ниже).
- Единая модель `DigestItem` (`kind`, `when`, `until`, `received`, `title`, `course`, `place`,
  `source`, `overdue`, `unread`, `important`, `url`, `raw`) и объект `sources` со статусом каждого
  источника (`ok`/`error`/`skipped`, `ms`, `warnings`). У писем, уведомлений и заявок `when: null`,
  время прихода — в `received`.
- Состав: `my_today` — расписание на сегодня, дедлайны (до конца завтра), непрочитанные письма
  SmartLMS, непрочитанные уведомления ЕЛК, активные заявки и задачи ЕЛК; `my_week` — 7 дней
  (сегодня + 6): расписание и дедлайны; `my_deadlines` — дедлайны LMS, окна СОП, активные заявки и
  задачи, экзамены/зачёты за `days` (по умолчанию 14). Дедлайны без даты остаются только в
  `my_deadlines`.
- Дедлайны LMS — календарь Moodle (`core_calendar_get_action_events_by_timesort`, один AJAX-вызов
  на все курсы, ключ кэша `lms:calendar:<от>:<до>`); обход таблиц курсов не реализован и не нужен.
  Отбора по `actionable` нет.
- Просроченные несданные видны **во всех трёх тулах**, в том числе у уже завершённых курсов
  (`OVERDUE_LOOKBACK_DAYS = 180`); фильтр «актуальные курсы» применяется только к будущим дедлайнам.
  Явный фильтр `courses` действует всегда; окна СОП им не ограничиваются.
- Расписание: ЕЛК основной, РУЗ — только запасной, если ЕЛК-расписание не ответило (иначе
  `ruz_schedule` = `skipped`). Экзамен — `lesson_type` по `/экзамен|зач[её]т|коллоквиум/i`.
- Частичные отказы: `runSource` не бросает, ошибка/таймаут источника — статус в `sources`, остальные
  элементы возвращаются; таймаут источника 40 с (`DigestPlan.sourceTimeoutMs`). Агрегат не
  кэшируется, состоит из кэшируемых клиентских вызовов.
- Корпоративная почта (IMAP, `mail_*`) в агрегаторы не входит — прямое решение пользователя.
- Вызовы AJAX Moodle (`listCourses`, `listActionEvents`) теперь хостятся на `/user/preferences.php`
  (`AJAX_HOST_URL`), а не на дашборде `/my/courses.php`: тот рендерится 7–9 с и упирается в 8-секундное
  ожидание рендера в `browser-session`. Результат тот же (19 курсов, 6 событий), тёплый
  `listActionEvents` 9 с → ≈ 3,4 с.

**Проверено вживую на реальном аккаунте (2026-10-14; один аккаунт, один день)**:
- Календарь Moodle отвечает через внутренний AJAX-сервис без ошибок; возвращает только несданное;
  просроченное несданное приходит с `overdue: true` и `action.actionable: false` (сдача закрыта);
  сданное в ответ не попадает. Поэтому отбора по `actionable` нет, а запасной обход таблиц курсов
  не реализован.
- Все 7 источников `ok`, `ruz_schedule` — `skipped` (ЕЛК-расписание работает).
- Колонки СОП («#», «Период», «Дата начала», «Дата окончания», «Статус»), формат дат «23:59
  25.10.2026 по московскому времени», статус «Анкета доступна» — активное окно; окно СОП не
  зависит от фильтра `courses`.
- Замеры (тёплая сессия, кроме холодного): `my_today` холодный процесс ≈ 17 с (первая страница
  процесса ≈ 8 с разово + последовательное открытие страниц), повтор из кэша ≈ 0 мс (TTL 2–5 мин);
  `my_week` ≈ 2,8 с; `my_deadlines(14)` ≈ 4,0 с; с фильтром курса ≈ 3,2 с.
- Оценка «агрегатор ≈ 1 с» из подпроекта 1 оказалась оптимистичной: реальный пол — открытие страниц
  (≈ 1–3 с на каждую) плюс AJAX календаря (1,6–3,2 с).
- `lms_*` через кэш: попадания в кэш ≈ 0 мс (закрывает пункт подпроекта 1).
- Изолированные проверки (в репозиторий не коммитятся — решение проекта «без тестов»): разбор дат,
  отображение событий календаря (в т.ч. просроченное с `actionable: false`, просроченное у
  завершённого курса), агрегация с частичными отказами/таймаутами и запасным РУЗ — все прошли.

**Не проверено**:
- Сквозной повтор при протухшем токене ЕЛК и протухшая SSO-сессия Keycloak.
- Форма задачи ЕЛК (на аккаунте `count: 0`) и активных заявок (на аккаунте их нет): маппинг
  по полям `title`/`name`/`text` — предположение.
- Точное написание `lesson_type` экзамена в расписании ЕЛК (в проверенном окне экзаменов не было;
  экзаменационный тест пришёл из Moodle как `lms_activity`).
- РУЗ как запасной путь из сети ВШЭ.
- Положительный случай фильтра `courses` — с дедлайнами в выбранном курсе (в первом курсе их не
  было).
- Правило «просроченное у завершённого курса» на реальном завершённом курсе (на аккаунте
  завершённых нет; проверено только изолированно).
- Другие аккаунты, роли и дни.

**Наблюдения и известный долг** (существовали до подпроекта 2, здесь не вводились):
- `openAuthenticatedPage` на первой странице каждого процесса пишет в stderr «страница …
  не отрендерилась за таймаут при проверке логина» (ожидание рендера 8 с) — фиксированная
  надбавка ≈ 8 с к первому вызову после запуска сервера; данные при этом приходят.
- Открытие страниц сериализовано `loginLock` в `browser-session.ts` вместе с ожиданием рендера,
  поэтому параллельность источников выигрыша не даёт; параллельный `listCourses` +
  `listActionEvents` в `lmsDeadlines` измеримого выигрыша не принёс — оставлен, не вредит.
- `/course/index.php` открывается ≈ 9,5 с (агрегаторами не используется).
- Цепочка расписания ЕЛК → РУЗ последовательна: при зависании обоих источников ожидание
  до ≈ 80 с (2 × 40 с), что выше типичного таймаута MCP-клиента ≈ 60 с. Маловероятно, не исправлено.

## Исправления надёжности и безопасности (2026-09-15)

Отдельная сессия аудита: три независимых ревью (два Explore-агента + скилл code-review) прошлись
по всей кодовой базе и нашли ~30 багов, все исправлены (`npm run build` чистый; критичное
дополнительно проверено изолированными локальными тестами — без реального `.env`/сети ВШЭ, см.
ограничение ниже).

- **Критично** (`src/auth/browser-session.ts`): битая сессия (`storage/hse-session.json`) или
  сбой запуска Chromium больше не блокируют сервер навсегда — rejected promise сбрасывается
  вместо вечного кэширования; `Page` больше не утекает при неудачном логине/навигации; параллельные
  SSO-логины сериализованы через lock (иначе гонка за cookies общего браузерного контекста);
  сессия на диске не перезаписывается сомнительным состоянием, если статус логина не удалось
  однозначно определить за 3 попытки; двойной `closeBrowserSession()` (напр. двойной `SIGINT`)
  идемпотентен.
- **Критично, безопасность** — SSRF-подобная уязвимость: `lms_open_page`/`elk_open_page`
  принимали произвольный абсолютный URL и открывали его в браузере с активной SSO-сессией ВШЭ.
  Добавлен `src/url-utils.ts#resolveScopedUrl` — allowlist по хосту (`edu.hse.ru` для LMS;
  `lk.hse.ru` + явно `pmo.hse.ru`-хелпдеск для ЕЛК), плюс нормализация ведущего слэша в
  относительных путях.
- **Критично, данные**: `src/dom-utils.ts#extractTable` — совпадающие заголовки колонок молча
  затирали значения друг друга (влияло на `lms_get_grades`/`lms_list_assignments`); таблицы без
  `<thead>` теперь тоже парсятся с сохранением семантики заголовков.
- `elk_get_schedule`: расчёт "сегодня" был на UTC (`toISOString()`), а `ruz_get_my_schedule` — на
  локальном времени; ночью по МСК (00:00–02:59) ЕЛК отдавал расписание на день назад. Унифицировано
  через `src/date-utils.ts#formatLocalDate`.
- Почта: `HSE_MAIL_APP_PASSWORD` стал обязательным для `mail_*`-тулов — fallback на `HSE_PASSWORD`
  убран (иначе пароль единого SSO ВШЭ уходил по IMAP/SMTP на серверы Яндекса). **Breaking change**
  для уже настроенных `.env` без этой переменной. Плюс: явные таймауты соединения (15-30с вместо
  библиотечных минут), метаданные вложений в `mail_read_message`, фолбэк текста для HTML-only
  писем, сортировка UID перед выборкой последних N писем.
- RUZ: понятная ошибка вместо `SyntaxError` при обращении вне сети ВШЭ (детект не-JSON ответа);
  `ruz_get_my_schedule` с несуществующим email больше не тащит `undefined` дальше в URL расписания.
- Мельче: `.positive()` на id-параметрах тулов, дедуп `addDays()`, ссылки-иконки без текста
  подхватывают `aria-label` в `dumpPage`, идемпотентный `shutdown()` в `src/index.ts` с таймаутом
  на случай зависшего браузера.

Не в скоупе (оставлено как техдолг): полная zod-валидация внешних ответов RUZ/ELK; выбор "той"
таблицы в `extractTable`, если по селектору совпало несколько (см. «Известный технический долг»).

**Ограничение верификации**: критичная логика (`date-utils`, `url-utils`, `dom-utils`,
идемпотентность `closeBrowserSession`, сброс битой сессии, отсутствие утечки `Page` при неудачной
навигации, обязательность `HSE_MAIL_APP_PASSWORD`) проверена изолированными локальными скриптами
через собранный `dist/`. Сценарии, требующие реального `.env`/сети ВШЭ (живой SSO-логин, RUZ из
кампуса, реальная почта, а также истуди/каталог ЕЛК, добавленные параллельно в этих же коммитах),
живьём не прогонялись — учётных данных в окружении не было.

## Живая проверка на реальном аккаунте (2026-09-15, сессия 2)

Пользователь предоставил реальные `HSE_EMAIL`/`HSE_PASSWORD` — впервые появилась возможность
проверить тулы вживую (а не только изолированными локальными тестами, см. ограничение выше).

- **Исправлен баг надёжности логина SmartLMS** (`src/auth/browser-session.ts#findKeycloakLoginHref`):
  edu.hse.ru не всегда автоматически редиректит на Keycloak, как считалось раньше (см.
  предыдущую формулировку комментария) — без уже активной Keycloak-сессии показывает страницу
  `/login/hselogin.php` со ссылкой «Войти», ведущей на собственный same-origin OIDC-мост
  `/auth/oidckc/` (который уже сам редиректит на `saml.hse.ru/.../openid-connect/auth`). Прежний
  код искал только `a[href*="openid-connect/auth"]` (формат ссылки ЕЛК), не находил такую ссылку
  на этой странице SmartLMS и **молча считал её уже залогиненной** — все `lms_*`-тулы тихо
  получали бы гостевую страницу вместо данных при первом заходе без сохранённой Keycloak-сессии.
  Найдено и исправлено при живой разведке `edu.hse.ru/my/courses.php`.
- **`lms_list_courses` переписан на внутренний AJAX-сервис Moodle** вместо парсинга ссылок — см.
  «Технический долг» в `ROADMAP.md`. Даёт прогресс прохождения, даты, категорию курса.
- **Найдена внутренняя почта SmartLMS** (`local_mail`, `lms_list_messages`/`lms_get_message`) —
  через живую разведку интерфейса Playwright MCP (клик по иконке письма на дашборде), а не по
  URL-догадке. Отдельная от корпоративной почты система переписки с преподавателями — см.
  `ROADMAP.md`.
- **Обнаружено ограничение `elk_get_profile`**: вкладки «ДПО»/«Прочее» на `/profile` — Vue-табы,
  контент неактивной вкладки не в DOM до клика, поэтому текстовый дамп видит только активную
  вкладку «Обучение». Внутри «Прочее» нашлась полезная read-only «История действий» — вынесена в
  отдельный `elk_get_login_history`; сама вкладка «ДПО» (форма для заполнения персональных
  данных) и «Вакцинация» — write-формы, не источники данных, не реализованы. Также добавлен
  `elk_get_notifications` (`/notification`).
- Новые `elk_*`-тулы этой сессии (`elk_get_academic_data`, `elk_list_tasks`,
  `elk_get_antiplagiat_status`, `elk_get_course_evaluation_status`, `elk_get_thesis_status`) —
  каждый проверен вживую на реальном аккаунте, детали в `ROADMAP.md`.

## Завершён плановый проход по ROADMAP.md (2026-09-15, финальная сессия)

По запросу пользователя пройден весь оставшийся бэклог `ROADMAP.md` в приоритетном порядке.
Итог — все реализуемые read-only находки конвертированы в тулы (см. выше); остальное осознанно
не реализовано:

- **Записывающие операции** (не тестируются автономно без присутствия/согласия пользователя,
  см. «Требования к безопасности»): `elk_order_certificate` (заказ справок), подача заявок на
  практику/академическую мобильность/социальную и повышенную стипендию (`window-lms.hse.ru`),
  запись на консультацию к психологам и отправка данных воинского учёта (обе — BPM-формы
  `bpm.hse.ru/Runtime/...`, найдены и задокументированы, submit не разведан). Сдача заданий в
  SmartLMS (`lms_submit_assignment`) — та же категория, требует `confirm: true`.
- **Вне скоупа персонального read-only MCP** (публичный некастомизированный контент):
  grants.hse.ru, studscience.hse.ru, career.hse.ru, library.hse.ru, studlife.hse.ru,
  volunteer.hse.ru — все подтверждены обычными CMS-страницами hse.ru без персонализации.
- **Не реализовано из-за неясного формата запроса** (не гадали, чтобы не сломать): история заявок
  на стипендию через общий DataTables-грид ЕЛК (`?r=st/request/history-dt`) — заменена более
  простым `elk_get_scholarship_history` через другой, GET-based эндпоинт с тем же смыслом.
- **Технический долг, оставленный явно**: кэширование access_token ЕЛК с TTL, rate-limiting между
  Playwright-действиями, проверка RUZ из сети ВШЭ (не тестируется из этого окружения). Smoke-тесты
  по модулям — намеренно НЕ добавлены: противоречат осознанному решению проекта «без тестов и
  линтера» (см. CLAUDE.md) — при желании изменить это решение нужен отдельный явный запрос
  пользователя, а не тихая реализация вопреки задокументированной архитектуре.

Подробности каждого пункта — в `ROADMAP.md`, раздел «Сделано (2026-09-15, финальный проход по
