# Подпроект №2 «Сводки и планирование» — спецификация дизайна

Дата: 2026-10-14. Статус: реализовано и проверено вживую на одном аккаунте за один день (итоги —
§13; что не проверено — там же). База: ветка `worktree-update`, коммит `e8bdc4c` (подпроект №1
«Надёжность и скорость» готов и проверен вживую). Разделы 5–9, 12 и 13 приведены в соответствие
с реализацией; расхождения с первоначальным черновиком отмечены в тексте.

## 1. Цель

Студент одним вызовом получает ответ на «что у меня сегодня», «что на неделе», «что горит» — без
ручного опроса десятка `elk_*`/`lms_*` тулов. Часть цели верхнего уровня «управлять учебной жизнью
полностью через MCP» (подпроект 2 из 4; №3 — проактивность, №4 — записывающие действия, в этот
подпроект не входят).

## 2. Решения (зафиксированы в диалоге)

| Вопрос | Решение |
|---|---|
| Состав «дедлайнов» | Задания LMS; тесты и прочие элементы LMS с датой закрытия; окна ЕЛК (период СОП, задачи, заявки); экзамены и зачёты |
| Формат вывода | Единый JSON: массив `items` одной схемы + объект `sources` со статусом каждого источника |
| Горизонт | Скользящие 7 дней. `my_deadlines` — параметр `days` (по умолчанию 14); просроченные включаются всегда |
| Состав `my_today` | Расписание, дедлайны, непрочитанная внутренняя почта LMS, непрочитанные уведомления ЕЛК, активные заявки и задачи ЕЛК |
| Корпоративная почта (IMAP, `mail_*`) | **Не входит ни в один агрегатор** — прямое решение пользователя |
| Курсы | Будущие дедлайны — только у актуальных курсов; просроченные несданные — у любых (в т.ч. завершённых); необязательный фильтр `courses` (см. §8) |
| Источник расписания | ЕЛК основной; RUZ — только запасной, если ЕЛК-расписание не ответило (решение автора, без дублей занятий) |

## 3. Подходы

- **A. Сервис `digest`, вызывающий клиентские функции напрямую (выбран).** Единая схема элемента,
  параллельный запуск источников, лимитер и кэш работают как есть.
- B. Агрегатор поверх MCP-тулов — лишний слой сериализации, хуже с частичными отказами. Отклонён.
- C. Один тул `my_overview({ scope })` — хуже для выбора тула моделью и для описаний. Отклонён.

## 4. Архитектура

Новый сервис `src/services/digest/` по образцу остальных (`client.ts` + `tools.ts`), плюс три
вспомогательных файла. Подключается в `src/index.ts` вызовом `registerDigestTools(server)`.

| Файл | Назначение | Зависимости |
|---|---|---|
| `types.ts` | `DigestItem`, `SourceStatus`, `DigestResult` | — |
| `parse.ts` | Чистые вспомогательные функции: даты и время, сортировка, определение экзамена, выбор курсов | — |
| `sources.ts` | По одному коллектору на источник; каждый возвращает `DigestItem[]`; не знает про MCP | клиенты `elk`/`lms`/`ruz`, `parse.ts` |
| `client.ts` | `getToday()`, `getWeek()`, `getDeadlines({ days, courses })`: запуск коллекторов, слияние, сортировка, `sources` | `sources.ts`, `parse.ts` |
| `tools.ts` | `registerDigestTools(server)`: тулы `my_today`, `my_week`, `my_deadlines`, zod-схемы, `runTool()` | `client.ts`, `mcp-utils.ts` |

Агрегаторы вызывают **клиентские функции**, не MCP-тулы. Существующий код сервисов почти не
менялся: в `src/services/lms/client.ts` экспортирован `fetchMoodleAjax`, добавлены
`listActionEvents` и `AJAX_HOST_URL`, а `listCourses` переведён на лёгкую страницу-хозяина AJAX
(см. §7).

## 5. Модель данных

```ts
type ItemKind =
  | "lesson" | "exam"                       // расписание
  | "assignment" | "lms_activity"           // LMS: задания / тесты и прочее
  | "elk_window" | "elk_task" | "elk_claim" // ЕЛК: СОП и т.п. / задачи / заявки
  | "lms_message" | "notification";         // входящие

interface DigestItem {
  kind: ItemKind;
  when: string | null;      // ISO 8601 с локальным смещением; null — дата не распознана
  until?: string;           // конец (занятие, окно)
  title: string;
  course?: string;
  received?: string;        // момент прихода/обновления письма, уведомления, заявки; у них when = null
  place?: string;           // аудитория/корпус для занятий
  source: string;           // имя коллектора, например "elk_schedule"
  overdue?: boolean;        // просрочено и не сдано, в т.ч. когда приём уже закрыт
  unread?: boolean;
  important?: boolean;      // isImportant уведомления ЕЛК
  url?: string;
  raw?: Record<string, unknown>; // нераспознанные поля (задачи ЕЛК, окна СОП)
}

interface SourceStatus {
  status: "ok" | "error" | "skipped";
  error?: string;
  warnings?: string[];      // нефатальные замечания источника
  ms: number;
}

interface DigestResult {
  generatedAt: string;
  window: { from: string; to: string };
  items: DigestItem[];
  sources: Record<string, SourceStatus>;
}
```

Сортировка `items`: просроченные первыми (по `when` по возрастанию), затем по `when`, затем
элементы без даты. Время — в локальной зоне процесса (как в существующем `date-utils.ts`).

## 6. Тулы и их источники

| Тул | Параметры | Содержимое |
|---|---|---|
| `my_today` | — | Расписание на сегодня (`elk_schedule`); дедлайны (`lms_deadlines`, `elk_windows`, экзамены из расписания) — все просроченные несданные + до конца завтрашнего дня; непрочитанные письма LMS (`lms_messages`); уведомления ЕЛК с `isRead === false` (`elk_notifications`); заявки с `active === true` (`elk_claims`) и задачи ЕЛК (`elk_tasks`) |
| `my_week` | — | Расписание на 7 дней (сегодня + 6); дедлайны (`lms_deadlines`, `elk_windows`, экзамены) на 7 дней + просроченные несданные. Без почты, уведомлений, заявок и задач (YAGNI; расширяется по запросу) |
| `my_deadlines` | `days?` (1–120, по умолчанию 14), `courses?` (массив id или подстрок названия) | `lms_deadlines`, `elk_windows`, `elk_tasks`, `elk_claims` (активные), экзамены/зачёты из расписания за `days`; просроченные всегда |

Коллекторы (`sources.ts`):

| Имя | Вызывает | Даёт |
|---|---|---|
| `elk_schedule` | `elk.getSchedule(from, to)` | `lesson`/`exam`. Экзамен — `lesson_type` совпал с `/экзамен\|зач[её]т\|коллоквиум\|exam/i` и не содержит «консультац» («консультация перед экзаменом» — обычное занятие). Время: `day.date` + `begin_time`/`end_time` |
| `ruz_schedule` | `ruz.getStudentInfo(config.hseEmail)` → `ruz.getSchedule` | Только если `elk_schedule` завершился ошибкой; в остальных случаях `status: "skipped"`. Не кэшируется |
| `lms_deadlines` | см. §7 | `assignment` / `lms_activity` |
| `lms_messages` | `lms.listMessages(50)` | `lms_message`, только `unread === true` |
| `elk_notifications` | `elk.getNotifications(50)` | `notification`, только `isRead === false` |
| `elk_claims` | `elk.listRequests()` | `elk_claim`, только `active === true` |
| `elk_tasks` | `elk.listTasks()` | `elk_task`; форма задачи на реальных данных не подтверждена (на проверенном аккаунте их нет) — поля кладутся в `raw`, `title` берётся из первого распознанного текстового поля (`title`/`name`/`text`), иначе «Задача ЕЛК» |
| `elk_windows` | `elk.getCourseEvaluationStatus()` | `elk_window`. Колонки строки (подтверждено вживую): «#», «Период», «Дата начала», «Дата окончания», «Статус»; даты вида «23:59 25.10.2026 по московскому времени». `when` — «Дата окончания»; строка без распознанной даты остаётся с `when: null`, строка целиком — в `raw`. Статус «Анкета доступна» — активное окно; статус с «заполнен/пройден/заверш/закрыт» без «не» перед словом (отрицательные формы, вроде «Анкета не заполнена», — окно открыто) или срок в прошлом — строка отбрасывается. Окно СОП **не** зависит от фильтра `courses` |

Источники `lms_messages`, `elk_notifications`, `elk_claims` кладут время в `received`; `when` у
них всегда `null`. В `my_today`/`my_week` дедлайны без распознанной даты отбрасываются (шум) и
остаются только в `my_deadlines`. **Просроченные несданные работы показываются во всех трёх
тулах** (прямое требование пользователя).

Реализация `my_today`/`my_week`/`my_deadlines` — выбор подмножества коллекторов и окна дат
(`DigestPlan`); общей логики слияния нет в тулах (она в `client.ts#buildDigest`).

## 7. Источник дедлайнов LMS

Единственная реализация — **календарь Moodle**: `lms.listActionEvents(from, to)` вызывает
`core_calendar_get_action_events_by_timesort` через AJAX-сервис Moodle (авторизация по sesskey, как
у `lms_list_courses`/`lms_list_messages`) одним запросом на все курсы, постранично по 50 событий, не более 6 страниц (300 событий)
за вызов (`CALENDAR_MAX_PAGES`): сверх этого результат усекается — события идут по
возрастанию времени, то есть отрезаются самые поздние; `listActionEvents` возвращает флаг
`truncated`, и коллектор добавляет предупреждение в `sources.lms_deadlines.warnings`.
Запасной обход таблиц курсов (`lms.listAssignments`) **не реализуется**: календарь подтверждён
живьём, а разбор русских дат в таблицах не понадобился (первоначальный черновик предполагал две
реализации).

- **Отбор по `actionable` не применяется.** Календарь возвращает только несданное; просроченное
  несданное приходит с `overdue: true` и `action.actionable: false` (приём закрыт), сданное в ответ
  не попадает. Фильтр по `actionable` спрятал бы ровно то, что пользователь хочет видеть.
- **Просроченные** ищутся за `OVERDUE_LOOKBACK_DAYS = 180` дней назад; элемент получает
  `overdue: true`.
- **Кэш** — на уровне клиентской функции: ключ `lms:calendar:<от>:<до>` (дневная гранулярность),
  `TTL.medium`; префикс `lms:` сбрасывается `hse_clear_cache`. Отдельного `lms:deadlines:*` нет.
- **Хост AJAX-вызовов** — `/user/preferences.php` (`AJAX_HOST_URL`), а не дашборд
  `/my/courses.php`: дашборд рендерится 7–9 с и упирается в 8-секундное ожидание рендера в
  `browser-session`; sesskey отдаёт любая лёгкая страница. Результат идентичен, тёплый вызов
  календаря 9 с → ≈ 3,4 с. Так же хостится `listCourses`.
- **Ошибка календаря** — источник `lms_deadlines` получает `status: "error"` в `sources`; запасного
  пути нет.
- Список курсов (`lms.listCourses`) и события запрашиваются параллельно; измеримого выигрыша это
  не дало (страницы открываются под `loginLock` последовательно), но не вредит.
- Таймаут источника — единый, см. §9.

## 8. Выбор курсов

`lms.listCourses()` → кандидаты: курсы с `visible === true` и `hidden === false`. Правило
«актуальный» (`enddate === null` либо `enddate` ≥ сегодня) применяется **только к будущим
дедлайнам**; **просроченное несданное сохраняется для любого видимого нескрытого курса, в том числе
уже завершённого** (требование пользователя, поправка к первоначальному черновику). Параметр
`courses` сужает выборку и действует всегда: число — точный `id`, строка — регистронезависимая
подстрока `fullname`/`shortname`. Если фильтр не нашёл ни одного курса, это ошибка источника
`lms_deadlines` с перечнем доступных названий, а не пустой результат. Фильтр относится только к
LMS-источникам; расписание, окна СОП и остальные источники ЕЛК им не ограничиваются.

## 9. Ошибки и частичные отказы

- Каждый коллектор запускается через `runSource` — обёртку, которая не бросает (эквивалент
  `Promise.allSettled`); падение или таймаут одного даёт `sources[<имя>] = { status: "error",
  error, ms }`, остальные элементы возвращаются. Нефатальные замечания — в `warnings`.
- Таймаут источника — 40 с по умолчанию, настраивается `DigestPlan.sourceTimeoutMs`. (Черновик
  предполагал вдвое меньше; холодному процессу нужно ≈ 17 с (в отдельных прогонах до ≈ 24 с): первая страница процесса ≈ 8 с разово
  плюс последовательное открытие страниц.) Цепочка «ЕЛК → РУЗ» последовательна, поэтому при
  зависании обоих источников ожидание может достичь ≈ 80 с — выше типичного таймаута MCP-клиента
  (≈ 60 с). Известно, маловероятно, отложено.
- Агрегат сам по себе не кэшируется: он состоит из кэшируемых частей (`elk:`/`lms:`), а RUZ в
  требованиях не кэшируется.
- RUZ вызывается только как запасной (ошибка `elk_schedule`), чтобы вне кампуса не платить
  таймаутом/редиректом за заведомо недоступный источник.
- Корпоративная почта не вызывается вовсе; параметр `HSE_MAIL_APP_PASSWORD` агрегаторам не нужен.
- Если упали все источники, тул всё равно возвращает `DigestResult` с пустым `items` и ошибками в
  `sources`, а не бросает исключение.

## 10. Нагрузка и ограничения платформы

- Каждый вызов клиентской функции держит максимум одну страницу; лимитер (3 одновременных,
  ≥300 мс между открытиями) работает внутри `openAuthenticatedPage`. Агрегатор не открывает страницы
  сам и не обходит лимитер.
- Реальное время (замер 2026-10-14, один аккаунт, §13): `my_today` с холодного процесса ≈ 17 с,
  повтор из кэша ≈ 0 мс; `my_week` ≈ 2,8 с; `my_deadlines(14)` ≈ 4,0 с. Оценка «агрегатор ≈ 1 с»
  из подпроекта 1 оказалась оптимистичной: пол задают открытия страниц (≈ 1–3 с каждое, они
  сериализованы `loginLock`) и AJAX календаря (1,6–3,2 с).
- Записывающих операций нет; новые тулы только читают.

## 13. Результаты живой проверки (2026-10-14)

Проверено на реальном аккаунте, **один аккаунт и один день**; ниже только форма и форматы данных
и замеры, без персональных значений.

**Календарь Moodle.** `core_calendar_get_action_events_by_timesort` через `fetchMoodleAjax` на
`edu.hse.ru` **работает** (HTTP 200, без `error`). Сработавшие аргументы: `{ timesortfrom,
timesortto, aftereventid, limitnum: 50, limittononsuspendedevents }`. Ответ: `{ events: [...],
firstid, lastid }`. Поля события: `id, name, modulename, activityname, instance, eventtype,
timesort, timestart, overdue (boolean), isactionevent, viewurl, url, course {id, fullname, ...},
action {name, actionable, url, ...}` и др.; `timesort` — unix-секунды. Календарь — единственный
источник дедлайнов LMS (§7).

**Семантика «просроченных».**
- Сданное задание в календарь не попадает вообще (задание в статусе «Отправлено для оценивания»
  в ответе отсутствует, хотя окно захватывало год назад).
- Просроченное несданное приходит с `overdue: true` и `action.actionable: false` (сдача уже
  закрыта). Поэтому фильтр по `actionable` запрещён: он спрятал бы ровно то, что пользователь
  хочет видеть.
- Будущий тест до открытия имеет `actionable: false` и `overdue: false` — тоже остаётся в списке.
- Модули в ответе: `assign`, `quiz`.

**Таблица заданий** (`lms_list_assignments`). Колонки `["Секция","Задания","Последний срок
сдачи","Ответ","Оценка"]`; срок — «понедельник, 5 октября 2026, 23:59»; статусы «Ответ не
представлен», «Нет ответа на задание», «Отправлено для оценивания»; строка-разделитель секции
приходит как `[""]`. Нужна только для справки: в коде агрегаторов не используется.

**Курсы.** 19 видимых, у 14 есть `enddate`, завершённых нет; все курсы с событиями проходят
правило «актуальный».

**Расписание ЕЛК** (`get-myschedule`). Формат — отдельные поля: `date` = `"2026-10-14"`,
`begin_time`/`end_time` = `"13:00"`/`"14:20"` (ISO собирается из даты и `HH:MM`). Поля занятия:
`auditorium, building, name, lesson_type, lesson_type_id, begin_time, end_time, lecturer,
lesson_number, parent_schedule, url1, url1_description, url2, url2_description`. Значения
`lesson_type`: «Проведение семинаров (студенты)», «Лекция», «Проведение практических занятий
(студенты)», «Научно-исследовательский семинар».

**СОП** (`getCourseEvaluationStatus`). Колонки `["#","Период","Дата начала","Дата окончания",
"Статус"]`; даты вида `"23:59 25.10.2026 по московскому времени"` (время перед датой); статус
«Анкета доступна» — признак активного окна.
