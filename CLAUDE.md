# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## О проекте

hsemcp — локальный MCP-сервер (stdio) для инфраструктуры НИУ ВШЭ: SmartLMS (edu.hse.ru),
Единый личный кабинет (lk.hse.ru). RUZ вынесен в отдельный репозиторий `hse-ruz-mcp`
(2026-10-23) — тулы `ruz_*` и запасной путь RUZ в сводках сюда не возвращать.

Корпоративная почта ВШЭ принципиально исключена из проекта по решению владельца: тулов и
зависимостей для неё не добавлять. Внутренняя почта SmartLMS (`lms_list_messages`,
`lms_get_message`) — другая система и остаётся.

Функциональные и нефункциональные требования — в `docs/requirements.md`, полная техническая разведка
(найденные эндпоинты, тупики, находки) — в локальных заметках разведки автора (в репозитории отсутствуют; в `.gitignore` стоит `docs/recon.md`), спецификации и планы подпроектов — в
`docs/superpowers/{specs,plans}/`. Отдельного файла со статусом нет: актуален `git log`. Если
меняются требования, обновляйте `docs/requirements.md`.

## Команды разработки

- `npm run build` — компиляция TypeScript (`tsc -p tsconfig.json`) в `dist/`.
- `npm run dev` — компиляция в режиме watch.
- `npm start` — запуск собранного сервера (`node dist/index.js`).
- `npx playwright install chromium` — нужно один раз после `npm install` для сервисов LMS/ЕЛК.
- Линтера нет; тесты — встроенный `node:test` (`npm test`, файлы `test/*.test.mjs`, без зависимостей):
  чистая логика покрывается тестами, браузерные части — заглушками и живой проверкой.
- Подключение к Claude Code: `claude mcp add hsemcp -- node <путь-к-проекту>/dist/index.js`.
- Перед первым запуском: `cp .env.example .env`, заполнить `HSE_EMAIL`, пароль положить в системное
  хранилище командой `npm run credentials:set` (запасной путь — `HSE_PASSWORD` в `.env`; см. README и
  `.env.example`).
- Тулы записи (`lms_submit_assignment`, `lms_delete_submission`, `elk_order_certificate`) выключены по умолчанию: включаются
  `HSE_ENABLE_WRITES=true` в `.env` (читается при старте процесса; без него их нет в `tools/list`).

## Архитектура

MCP-сервер на `@modelcontextprotocol/sdk` (stdio-транспорт). `src/index.ts` создаёт `McpServer` и
регистрирует тулы всех сервисов через `registerXTools(server)`; при `SIGINT`/`SIGTERM` закрывает
общий Playwright-браузер перед выходом.

Каждый сервис живёт в `src/services/<name>/` и состоит из двух файлов:
- `client.ts` — логика похода во внешнюю систему, без зависимостей от MCP SDK.
- `tools.ts` — экспортирует `registerXTools(server)`, оборачивает функции клиента в
  `server.registerTool(...)` с zod-схемой входа и вызывает их через `runTool()`
  (`src/mcp-utils.ts`) — единая обёртка, которая сериализует успешный результат в JSON-текст,
  а исключение превращает в `isError`-ответ вместо выброса.

Доступ к данным ВШЭ:
- **SmartLMS и ЕЛК** (`services/lms/`, `services/elk/`) — через общий Playwright-браузер
  `src/auth/browser-session.ts` (через `withPage`), который проходит единый SSO ВШЭ
  (Keycloak, `saml.hse.ru`, realm `hse`) при первом обращении и переиспользует контекст/сессию
  между вызовами тулов (`storage/hse-session.json` — переживает перезапуск сервера). SmartLMS —
  Moodle; парсинг материалов/заданий/оценок опирается на стандартные Moodle URL-паттерны
  (`/mod/<type>/view.php?id=`), а не на CSS-классы (тема оформления ВШЭ кастомизирована).
  ЕЛК (`lk.hse.ru`) вне `/profile` не имеет документированной структуры, поэтому его тулы
  (`elk_open_page`, `lms_open_page`) возвращают через `dom-utils.ts#dumpPage` сырой видимый
  текст + ссылки страницы вместо разобранных полей — модель извлекает нужное сама. ЕЛК также
  даёт JSON API с `Authorization: Bearer <access_token>` из localStorage (`elk_get_schedule`,
  `elk_get_user_info`, `elk_search_services`, `elk_list_requests`) — токен добывается тем же
  Playwright-логином.
- **istudy.hse.ru** (зачётка) не поддерживается: тулы `istudy_*` удалены 2026-10-23. Вход проходит без MAX, но данные закрыты двухфакторным подтверждением через MAX (HTTP 412 на `GET /api/auth/two-factor/required` после клика по «Зачетная книжка»), а эндпоинты после 2FA неизвестны; обход 2FA не предусмотрен. Оценки по курсам — `lms_get_grades`. Не возвращать без новой разведки (§12 спецификации подпроекта 3).
- **Сводки** (`services/digest/`) — агрегаторы `my_today`/`my_week`/`my_deadlines`. Сервис вызывает
  клиентские функции `elk`/`lms`, а не MCP-тулы. `buildDigest(plan, collectors)` запускает
  коллекторы параллельно (набор `Collectors` внедряется — так логику можно проверять без сети),
  каждый через `runSource` с таймаутом 40 с; отказ источника превращается в статус в `sources`
  (`ok`/`error`/`skipped`), а не в исключение. Все источники приводятся к единой модели
  `DigestItem`. Дедлайны LMS берутся из календаря Moodle (`lms.listActionEvents`, один запрос, постранично по 50, не более 300 событий;
  фильтра по `actionable` нет — просроченное несданное приходит с `actionable: false`); просроченные
  несданные видны во всех трёх тулах, «актуальные курсы» отсекают только будущие дедлайны.
  Расписание — только ЕЛК (запасного источника нет). AJAX-вызовы Moodle хостятся на
  `/user/preferences.php`, а не на дашборде.
- **Снимки и изменения** (`services/changes/`) — `hse_changes`/`hse_changes_reset`: «что изменилось»,
  а не «что есть» (это `digest`). Извлекатели (`extractors.ts`) приводят шесть источников (календарь
  Moodle, окна СОП, расписание ЕЛК на 14 дней, сообщения LMS, уведомления и заявки ЕЛК) и источник
  на курс (`lms_grades:<id>`, только по явной просьбе `scopes`, пул ≤ 3, бюджет 90 с) к фактам со
  стабильным `id`; `diff.ts` сравнивает с базой источника с учётом покрытия скользящих окон;
  `store.ts` пишет `storage/changes/state.json` атомарно под lock-файлом. Хранение: база на каждый
  источник (отказ одного не трогает остальных, первый запуск источника создаёт базу без событий) и
  журнал событий (30 дней, ≤ 500) с курсором по областям. Курсор двигает только `ack` = `ackSeq`
  предыдущего ответа (в том же вызове, где он передан); события, выданные самим ответом, курсор не
  двигают, поэтому ничего не теряется, если ответ не дошёл; при `persisted: false` `ackSeq` и `seq`
  равны `null`. Свежесть — `maxAgeMs` (60 с, `fresh: true` — 0), не `clearCache`. Подробности — спецификация подпроекта 3.
  Ограничения и непроверенное (потолки ответа и журнала, `removed`, усечение календаря — в README):
  моменты разбираются без пояса машины (UTC у Moodle, наивное МСК у ЕЛК), но границы окон — по
  локальной полуночи машины, смена пояса не проверялась; `overdue` выводится из часов
  (`cause: "clock"`); сдвиг срока: id события Moodle предполагается стабильным, тогда `changed` по `due`
  (на живых данных не проверялось; при смене id выйдет `removed` + `added`). Долг по `invalidates`
  (неизвестное имя бросало после выполненной записи) закрыт подпроектом 4: имена проверяются до загрузки,
  для записи есть режим `cache: false`. Проверено вживую на одном аккаунте (спека §18, «Проверка
  реализации»); `added`/`changed`/`moved` — только имитацией правки базы.
- **Запись** (`services/writes/`, подпроект 4, спека `2026-10-18-write-operations-design.md`) — общий
  каркас записывающих тулов без зависимостей от MCP SDK: `types.ts`, `token.ts` (ключ HMAC
  `storage/writes/key`, `previewToken`, `targetId`), `journal.ts` (`storage/writes/journal.json`),
  `outbox.ts` (проверка файлов из папки «исходящих»), `runner.ts#defineWrite` (протокол). Адаптер
  операции (`observe`/`describe`/`payloadOf`/`execute`/`verifyOnly`) живёт в сервисе:
  `services/lms/submissions.ts`, тулы `lms_submit_assignment` и `lms_delete_submission` регистрируются в
  `services/lms/tools.ts`, а `elk_order_certificate` (адаптер `services/elk/certificate.ts`) — в
  `services/elk/tools.ts`, оба только при `config.writesEnabled` (`HSE_ENABLE_WRITES=true`, по умолчанию
  выключено, читается при старте); аннотации, схема `confirm`/`previewToken`/`acknowledgeUnknown` и
  одно на процесс уведомление «тулы записи выключены» общие — `services/writes/gate.ts`. Заказ справки
  (`serviceId` — число `components` из `url` результата `elk_search_services`, не поле `id`)
  необратим (отмены в ЕЛК нет); форма читается без выбора и отправки (сухой прогон с пустым `fields` — отказ `planCertificate` со
  списком обязательных полей и их вариантов: так узнают, что выбирать), заполняются только выпадающие
  списки (поле другого типа, обязательное и не заполненное формой, и варианты «…в дополнительном
  поле» — отказ). Исход — только `confirmed`/`unknown`, но на живом сервисе
  `confirmed` недостижим: справки «Сервиса Студент» в `/api/claims` (его читает `elk_list_requests`) не
  видны, `newClaims: 0` не означает неудачу (пассивная проверка `classifyCertificateOutcome` и опрос
  истории оставлены для форм, чьи заявки видны). Каждый `unknown` (в том числе сбой или дедлайн после
  точки невозврата: хук адаптера `unknownWarnings`; дедлайн коммита заказа — 45 с) несёт предупреждение
  `MANUAL_CHECK_WARNING`: сверка только вручную на странице «Заявки» в lk.hse.ru, заказ не повторять.
  Заказ выполнен вживую один раз на одном аккаунте и дошёл (ручная проверка: ровно одна новая заявка);
  тул ответил `unknown` (спека §17, одиннадцатый проход).
  Протокол: сухой прогон (только чтение, без `confirm`) → `previewToken` (HMAC-SHA256, 15 мин, привязан к
  операции, цели, режиму, файлам (имя + sha256) и отпечатку состояния страницы) → `confirm: true` +
  токен → журнал `sending` → точка невозврата → проверка повторным чтением → исход
  `confirmed`/`rejected`/`unknown`. После `unknown` автоповтора нет: повтор того же токена только
  проверяет чтением, новая запись по цели требует `acknowledgeUnknown: true` и ручной проверки сайта.
  Одновременно — одна запись на процесс. Журнал: 90 дней, ≤ 200 записей, только технические поля
  (`at, op, tokenId, targetId, stage, outcome?, durationMs?, errorClass?`), без содержимого, имён
  файлов, ФИО и id. Папка «исходящих» — `storage/outbox/` или `HSE_OUTBOX_DIR`: ≤ 10 файлов, только
  имена без путей, обычные непустые файлы, `realpath` внутри папки; папка не может быть корнем проекта
  или `storage` либо содержать их (допустима только `storage/outbox`); файлы не перемещаются и не
  удаляются, отправляемые байты сверяются с sha256 из сухого прогона, файл крупнее 64 МиБ отклоняется
  (результат нельзя проверить). Запись идёт через `defineResource` с `cache: false` (без кэша и
  дедупликации; `invalidates` сбрасывает `lms.assignments`/`lms.calendar` после точки невозврата при
  любом исходе) и `ctx.commit()`: после него отмена клиента и исходный дедлайн вызов не прерывают, действует
  дедлайн коммита 20 с (`src/commit.ts`), симметрично `commit()` у `withPage`. Общие блокировка файлов и
  атомарная запись вынесены в `src/fs-lock.ts` (используют `changes` и журнал). Защита присутствия — запрос
  разрешения клиента MCP на каждый вызов (тулы с `destructiveHint`); сервер присутствие проверить не
  может, поэтому тулы записи нельзя добавлять в автоматически разрешённые. `lms_open_page`/`elk_open_page`
  отклоняют URL с `sesskey` и страницы `/mod/assign/` с `action=` (`url-utils.ts#assertReadOnlyPath`).

`src/config.ts` читает `.env` по пути относительно расположения самого файла (не `process.cwd()`),
потому что сторонние хосты (Claude Desktop и т.п.) запускают stdio-сервер с произвольным рабочим
каталогом. Обязательные значения (`HSE_EMAIL` и пароль: окружение, системное хранилище или `.env`) читаются лениво
через геттеры и бросают понятную ошибку при отсутствии.

Надёжность и скорость (общая инфраструктура поверх сервисов):
- `src/auth/browser-session.ts#withPage(url, fn, { deadlineMs, signal })` — единственный способ
  открыть страницу: проходит SSO, вызывает `fn`, в `finally` закрывает страницу и возвращает слот
  лимитера; по дедлайну (45 с) или сигналу страница закрывается, слот освобождается. Вложенный
  `withPage` запрещён (ошибка вместо зависания). Замок входа держится только на фактический вход и
  повторную проверку после него, а не на открытие и ожидание рендера страницы; сессия на диск
  пишется атомарно. `PageCallContext.commit()` вызывает код записи в точке невозврата: после него
  сигнал клиента и исходный дедлайн страницу не закрывают.
- `src/limiter.ts` — потолок 3 одновременных страницы и пауза ≥300 мс между открытиями; слот имеет
  аренду (дедлайн + 5 с) как страховку от утечки; прямые API-запросы идут не чаще 1 в 100 мс.
  Пороги не измерены на антибот-защите ВШЭ.
- `src/resource.ts#defineResource` — кэшируемый ресурс: имя `<домен>.<id>`, ключ, TTL, загрузчик,
  срез `project` после кэша, дедлайн загрузки. Вызов принимает `{ signal, maxAgeMs }`: `maxAgeMs`
  берёт запись не старше N мс, не сбрасывая кэш (`clearCache` бьёт по всем доменам). Результат в
  кэше заморожен (мутация даёт `TypeError`). Домены `elk:`/`lms:` — по префиксу работает `clearCache` (тул
  `hse_clear_cache`); `invalidates` у записывающих ресурсов (`cache: false`, см. «Запись») сбрасывает
  ресурсы по имени; имена проверяются в начале вызова, до загрузки.
  Хранилище — `src/cache.ts` (память, TTL, дедупликация, лимит 200 записей); на диск ничего не
  пишется.
- Прямой путь ЕЛК (`services/elk/client.ts`): токен кэшируется до `exp` JWT, запросы идут через
  `context.request`. 401/не-JSON сбрасывают токен, 403 нет; после двух отказов один заход через
  страницу, и если он прошёл — выключатель (`src/breaker.ts`) на 10 минут отправляет запросы через
  страницу, затем проба (параллельные вызовы могут пробовать одновременно). Расписание ЕЛК грузится и кэшируется по неделям; календарь LMS —
  по корзинам правой границы (7/14/30/60 дней).

`src/dom-utils.ts` — переиспользуемые Playwright-утилиты для сервисов LMS/ЕЛК: `extractTable`
(HTML-таблица thead/tbody → массив объектов), `extractGradeTable` (журнал оценок Moodle
`table.user-grade`: имя из `th.column-itemname`, колонки по классам `column-*`; `extractTable` для
него непригоден — сдвигает ключи; на нём построен `lms_get_grades` через `lms.grade-items`,
нераспознанная таблица курса даёт ошибку `unsupported grade table`) и `dumpPage`
(универсальный снимок страницы: текст + ссылки — для порталов с неизвестной вёрсткой).

## Добавление нового сервиса

Создать `src/services/<name>/` с `client.ts` (логика) и `tools.ts` (`registerXTools(server)`),
подключить вызовом в `src/index.ts` — по образцу существующих сервисов.

## Известные ограничения

- Селекторы ЕЛК за пределами `/profile` не проверены вживую — структура остальных разделов
  неизвестна.
- ЕЛК: запись есть только для заказа справки (`elk_order_certificate`, при `HSE_ENABLE_WRITES=true`);
  подача заявок не реализована. LMS: запись есть только для сдачи, правки и удаления ответа файлами
  (при `HSE_ENABLE_WRITES=true`).
- Заказ справки в ЕЛК необратим; свободный текст, даты, файлы и варианты «…в дополнительном поле» не
  поддерживаются (отказ), поля, которые форма дорисовывает после выбора варианта, сухой прогон не видит.
  `rejected` для заказа не выносится; `confirmed` недостижим (см. «Запись»).
- Запись в LMS: онлайн-текст не поддерживается (параметр `text` отклоняется до записи). У заданий без
  отдельного шага «Отправить на оценку» само сохранение сразу отправляет работу на оценку — `draft` этого
  не исключает; сам шаг «Отправить на оценку» тул не выполняет (если после сохранения статус остался
  черновиком, `submit` даёт `unknown` со стадией `draft-saved`). Просроченные и закрытые задания
  отклоняются, даже если поздняя сдача может быть открыта. Нераспознанный класс статуса сдачи — отказ
  (класс черновика `submissiondraft` вживую не наблюдался). Существующий файл ответа крупнее 64 МиБ
  блокирует сухой прогон. Проверено на одном аккаунте за один семестр.
- `hse_changes`: если часы машины однажды ушли вперёд, проверка «снимок устарел» пропускает источники
  (`skipped: "снимок устарел: база новее"`) до `hse_changes_reset` или пока время не догонит; данные
  не теряются (финальное ревью, M-3).

## Roadmap

Разведка и открытые находки — в локальных заметках разведки (не в репозитории), известные ограничения подпроекта 2 — в §13
его спецификации. v1 (SmartLMS, ЕЛК-профиль/расписание/
каталог/заявки, SSO) готова, istudy-зачётка удалена (2FA через MAX, см. выше); подпроект 2 «Сводки и планирование»
(`my_today`/`my_week`/`my_deadlines`) тоже готов, проверен вживую на одном аккаунте; подпроект 3
«Проактивность: снапшоты и diff» (`hse_changes`) реализован и проверен вживую на одном аккаунте
(спека §18); подпроект 4 «Записывающие операции» — сдача, правка и удаление ответа на задание LMS
(`lms_submit_assignment`, `lms_delete_submission`) и заказ справки в ЕЛК (`elk_order_certificate`), все за
