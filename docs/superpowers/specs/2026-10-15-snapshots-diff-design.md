# Подпроект №3 «Проактивность: снапшоты и diff» — спецификация дизайна

Дата: 2026-10-15. Статус: **дизайн утверждён в диалоге, реализация не начата, живая проверка не
проводилась**. База: ветка `snapshots-diff` от `origin/reliability-rework` (PR №1 ещё открыт;
после его слияния ветка переносится на `master`). Подпроект 2 «Сводки» (`digest`) уже в базе.
Дизайн прошёл независимое ревью агента на `opus` (§17): 2 блокирующих и 9 существенных замечаний
учтены в этой версии.

## 1. Цель

Вместо «что есть сейчас» (`digest`) отвечать на «что изменилось с прошлого раза»: новые и
изменённые дедлайны и задания, изменения расписания, новое входящее и смена статусов заявок, новые
оценки. Часть цели верхнего уровня «управлять учебной жизнью через MCP» (подпроект 3 из 4; №4 —
записывающие действия — сюда не входит).

## 2. Решения (зафиксированы в диалоге)

| Вопрос | Решение |
|---|---|
| Что важно | Задания и дедлайны; расписание; входящее и заявки; оценки |
| Режим получения | **Только по запросу тулом.** Таймеров и фоновых процессов нет |
| Оценки | Отдельная область (`grades`), только по явной просьбе (дорогая) |
| Хранение | Подход B: последняя база по источнику + журнал событий с курсором |
| Выдача без потери | «Сигнал отмены + явное подтверждение (`ack`)» вместе |
| Корпоративная почта (IMAP) | Исключена из проекта целиком; удаляется **отдельной веткой и PR до №3** (в этот дизайн не входит) |
| istudy | Вне №3 (§12). Оценки — только журнал LMS |
| Документация | Требования — `docs/requirements.md`, архитектура — `CLAUDE.md`, итоги живой проверки — раздел в этой спецификации |

## 3. Подходы

- A. Только последний снимок на область. Отклонён: событие теряется, как только база сдвинулась и
  ответ не дошёл; «за неделю» невозможно.
- **B. Последняя база по источнику + журнал событий с курсором. Выбран.**
- C. Только хэши фактов. Отклонён: «было 7, стало 8» и «срок сдвинулся с X на Y» невозможны.

## 5. Модель фактов

Факт: `{ id, scope, kind, title, course?, attrs }`. `id` стабилен между снимками, в `attrs` только
отслеживаемые поля. Не входят в факт: `updated`, время получения, url с query, `raw`, `actionable`,
порядок, свободный текст. Сравниваются только `attrs`, в каноническом виде (§6).

Источник → факты; **единица базы — источник** (`lms_calendar`, `elk_windows`, `elk_schedule`,
`lms_messages`, `elk_notifications`, `elk_claims`, `lms_grades:<courseId>`).

| Область | Источник | `id` | `attrs` | События |
|---|---|---|---|---|
| `deadlines` | `lms.listActionEvents(today−180д … today+60д)` | id события Moodle | срок (`due`), название | `added`, `changed(due)`, `removed`, `overdue` |
| `deadlines` | `elk.getCourseEvaluationStatus` (окна СОП) | период | срок окончания, статус | `added`, `changed`, `removed` |
| `schedule` | `elk.getSchedule(today … today+14д)` | `дата\|начало\|название\|тип` | конец, аудитория, корпус | `added`, `changed`, `removed`, `moved` |
| `inbox` | `lms.listMessages(200)` | id сообщения | заголовок | только `added` |
| `inbox` | `elk.getNotifications(100)` | id уведомления | заголовок | только `added` |
| `claims` | `elk.listRequests(500)` | `num` | `stateName`, `active` | `added`, `changed` |
| `grades` | `lms.getGrades(courseId)` по актуальным курсам | `courseId\|путь категорий\|название элемента` | оценка (текст ячейки) | `added` (только с непустой оценкой), `changed` |

Правила:

1. **«Пропало из календаря» ≠ «сдано».** Календарь не показывает сданное, но так же исчезает
   завершённое без сдачи, удалённое и вышедшее за окно. Событие `removed` формулируется как
   «пропало из календаря».
2. **`overdue` не входит в `attrs`.** В Moodle `overdue = timesort < now` — это ход часов, а не
   изменение данных. Событие `overdue` порождается, когда `baseline.takenAt < due ≤ now`, а элемент
   всё ещё в календаре. Оно помечено `cause: "clock"`.
3. **Прочтение — не событие.** В `inbox` порождаются только `added`; пропажа письма/уведомления
   из выборки `removed` не даёт.
4. **Покрытие (`coverage`) у каждого источника, имеющего скользящее окно** — см. §11. `added` и
   `removed` считаются только для фактов, чьё значение оси лежит в пересечении старого и нового покрытий.
5. **Расписание.** `id` включает начало, поэтому перенос выглядит как `removed` + `added`. После
   diff — проход, который склеивает пару с одинаковыми (название, тип) внутри пересечения покрытий в
   одно событие `moved` (`from`/`to`: дата, начало, аудитория). Неоднозначная склейка (несколько
   кандидатов) не выполняется. Сдвоенные пары и подгруппы различаются началом в `id`.
6. **Оценки.** Существующий `extractTable` непригоден: имя элемента Moodle рендерит в `<th>`
   (`column-itemname`), а слева стоят `leader`-ячейки с `rowspan`; `extractTable` читает только `td`
   и сопоставляет их с `thead th` по индексу. Нужен `extractGradeTable`: имя — из `th.column-itemname`,
   путь категорий — из вложенности, колонки — по классам (`column-grade` и т.п.), не по индексу.
   В `attrs` кладётся **только** оценка: «Процент» и «Вклад» пересчитываются каскадом от любой оценки.
   Новый элемент с пустой оценкой («-») база запоминает, но событием не считает. Если разбор не
   нашёл колонки, источник получает статус `error: "unsupported grade table"`, а не ложные события.

## 6. Нормализация

- Строки: Unicode NFC, `trim`, схлопывание пробельных символов, регистр не меняется.
- **Моменты — без участия часового пояса машины.** Moodle (unix-секунды) → `YYYY-MM-DDTHH:mmZ` в
  UTC. ЕЛК и СОП (локальные строки даты и времени МСК) хранятся как наивное МСК-время
  `YYYY-MM-DDTHH:mm`, без перевода через `Date` и без смещения. Сравниваются строки. Поэтому смена пояса ОС
  не порождает массовых `changed`. (МСК без перехода на летнее время с 2014 г.; риск только от пояса
  машины.) Это отличается от `toLocalIso` в `digest`, который пишет смещение машины.
- Отпечаток `attrs`: JSON с отсортированными ключами; `null`, `undefined` и пустая строка равны.
- Данные из кэша заморожены (`Object.freeze`): нормализация копирует, а не мутирует.

## 7. Хранение

Один файл `storage/changes/state.json` (каталог `storage/` уже в `.gitignore`). Путь вычисляется от
расположения модуля, а не от `cwd` (как `config.ts`). Пишется целиком (порядка 100–300 КБ).

```
{ version, rev, nextSeq, issued, lost: { [scope]: n },
  baselines: { [source]: { takenAt, coverage?: {from,to}, facts: { [id]: Fact } } },
  journal:   [ { seq, at, scope, source, type, cause?, id, kind, title, course?, fields?: [...] } ],
  seen:      { [scope]: seq } }
```

**Не пишется никогда:** токены и всё из `storageState`, email, ФИО (`sender`, `executorFio`,
`createdBy*`), тела писем, текст уведомлений и заявок (у заявки `title` = только `service`), url с query,
`raw`. Названия курсов, оценок, темы писем и заголовки уведомлений остаются — без них diff не читается;
тема письма может содержать ФИО, это **принятый риск**, локальный файл, сброс — `hse_changes_reset`.

**Нумерация.** `seq` глобален по всем областям и выдаётся `nextSeq++` только при успешном коммите
(событие без записи не получает `seq`). `nextSeq` монотонен: не сбрасывается ни срезом журнала, ни
`hse_changes_reset`. После `.corrupt` нумерация может начаться заново **вместе** со сбросом `seen`.

**Срок жизни.**
- Журнал: событие старше 30 дней срезается **только если его `seq` ≤ min(`seen`)** по областям;
  жёсткий потолок 500 событий срезает старейшие, в том числе невыданные. Срезанное невыданное
  учитывается в `lost[scope]`; ответ сообщает `gap` (§10).
- Базы: перезаписываются. База `lms_grades:<id>`, не обновлявшаяся 90 дней (курс исчез из актуальных),
  удаляется.
- Очистка: `hse_changes_reset`, либо удаление файла (штатный «первый запуск»).

**Права.** Создаётся с `0o600`, но на Windows (платформа проекта) `mode` управляет только флагом
записи, разграничения owner/group/others нет: реальная защита — ACL профиля пользователя, как у
`storage/hse-session.json`, который чувствительнее. Больше не обещается.

**Целостность и отказы ввода-вывода.**
- `.corrupt` — **только** при `JSON.parse` или схеме, не прошедших проверку; имя с меткой времени, прежние
  `.corrupt` не затираются.
- Ошибка чтения/переименования (`EPERM`/`EACCES`/`EBUSY` из-за антивируса, индексатора, другого
  процесса) — повторы с короткой паузой (≈5 попыток), затем `persisted: false` без записи и без
  `.corrupt`.
- `version` новее известной (откат на старый код) — файл не трогается, ответ `error`, `persisted: false`.
- Запись: во временный файл с `process.pid` и `rename` (как `saveStorageState`), повторы для `rename`.
- Параллельные процессы (два хоста): lock-файл `state.json.lock` через `fs.openSync(..., "wx")`
  только на цикл «прочитать → пересчитать diff от свежей базы → записать»; сбор данных идёт вне
  блокировки; устаревшая блокировка (> 30 с) снимается. Внутри процесса — мьютекс. Проверка `rev`
  сохраняется как дополнительная.

## 8. Свежесть кэша

`clearCache` перед снимком отвергнут: `generation` общий на весь кэш, поэтому любой сброс запрещает
запись всем идущим загрузкам во всех доменах и убирает in-flight-дедупликацию. Вместо этого —
требование свежести на уровне вызова.

- `ResourceCallOptions.maxAgeMs?`. `Entry.storedAt` — **момент старта** загрузки. Запись кэша годна,
  если `expiresAt > now` и `now − storedAt ≤ maxAgeMs`. In-flight принимается, только если стартовал не
  раньше `now − maxAgeMs`; иначе запускается новая загрузка и становится актуальной для ключа.
  Запись в хранилище разрешена, только если `startedAt ≥ storedAt` текущей записи — старая загрузка,
  завершившаяся позже, не затирает свежую.
- Дефолт снимка — `maxAgeMs = 60 с` (сразу после `my_today` страницы не открываются повторно);
  `fresh: true` → `0`. `maxAgeMs: 0` — «перечитай и сохрани», а не «не кэшируй».
- Восемь функций: `elk.getSchedule` (передаёт `opts` в каждый недельный вызов `elkScheduleWeek`),
  `getNotifications`, `listRequests`, `getCourseEvaluationStatus`; `lms.listActionEvents`, `listMessages`,
  `listCourses`, `getGrades`.
- Полнота: ключи кэша от `limit` не зависят, загрузка всегда берёт максимум, `limit` режет выдачу —
  снимок вызывает с максимумом (`getNotifications(100)`, `listMessages(200)`, `listRequests(500)`).
- `hse_changes` не вызывает `clearCache`.

## 9. Лимитер и бюджет оценок

Снимок не обходит лимитер (3 страницы, ≥300 мс) и не держит вложенных `withPage`. Дедлайн ресурса 45 с
**включает ожидание слота лимитера**, поэтому запускать все курсы оценок через `Promise.all` нельзя:
хвост очереди упал бы со статусом `error` по таймауту.

- `grades`: пул ≤ 3 одновременных загрузок; новые курсы не запускаются, когда бюджета области (90 с)
  не хватает; незапущенные получают `skipped`, их базы прежние.
- Порядок обхода — по давности последнего снимка курса (самые старые первыми), чтобы один и тот же
  хвост не пропускался вечно.
- Только актуальные курсы (`selectCourses`); фильтр `courses` ограничивает набор.
- Прочие области: источник ограничен дедлайном ресурса и таймаутом `runSource` (40 с).
- Оценка по F4/F7 подпроекта 1 — десятки секунд на холодном процессе; **это оценка, не замер**.

Страницы по областям: `deadlines` 2 (календарь + СОП), `inbox` 1 (LMS-сообщения; уведомления ЕЛК —
прямой API), `claims`/`schedule` 0 (прямой API; холодному процессу нужна 1 страница на токен),
`grades` 1 (`listCourses`) + N курсов.

## 10. Интерфейс

### `hse_changes`

| Параметр | Значение |
|---|---|
| `scopes?` | подмножество `deadlines`, `schedule`, `inbox`, `claims`, `grades`; по умолчанию все **кроме** `grades` |
| `courses?` | фильтр для `grades` (число — id, строка — подстрока названия) |
| `fresh?` | `true` → `maxAgeMs: 0`; по умолчанию 60 с |
| `since?` | `"7d"` или ISO: вернуть журнал за период; `seen` не меняется |
| `ack?` | `seq`, до которого события **получены**; сдвигает `seen` для областей вызова |

Порядок: (1) если есть `ack` — применить к `seen` (с ограничением `ack ≤ issued`; больше — игнорируется
с предупреждением); (2) снять факты источников; (3) под lock-файлом пересчитать diff от свежей базы и
**одним коммитом** записать базы и события; (4) вернуть события с `seq > seen[scope]`. **Курсор в этом
же вызове не двигается**: событие не теряется, даже если ответ не дошёл (таймаут SDK 60 с, остановка
фоновой задачи). Неподтверждённое возвращается снова — дубль допустим, потеря нет. `extra.signal`
останавливает незапущенную работу (курсы, источники) и пропускает шаг коммита, если отмена пришла до
него; для корректности он не нужен, а для того, чтобы не тратить слоты лимитера и не писать после отмены.

Выдача упорядочена по `seq` по всем областям сразу; потолок 200 событий срезает **префикс** (поэтому
`ack = ackSeq` никогда не «перепрыгивает» невыданное); `omitted` — сколько осталось. `issued` — наибольший
`seq`, когда-либо возвращённый в ответе; он записывается тем же коммитом (шаг 3) и ограничивает `ack`.
`ack` применяется ко всем областям текущего вызова: `seen[scope] = max(seen[scope], ack)`; области вне
вызова не затрагиваются.

Ответ:

```json
{
  "takenAt": "…",
  "scopes":  { "deadlines": { "status": "ok|baseline|partial|error", "facts": 42, "warnings": [] } },
  "sources": { "lms_calendar": { "status": "ok|error|skipped", "ms": 2800, "error": "…" } },
  "changes": [ { "seq": 17, "at": "…", "scope": "deadlines", "type": "changed",
                 "kind": "assignment", "title": "…", "course": "…",
                 "fields": [ { "field": "due", "from": "…", "to": "…" } ] } ],
  "ackSeq": 17, "omitted": 0, "gap": { "lostEvents": 0 }, "persisted": true
}
```

`ackSeq` — значение, которое следующий вызов передаёт в `ack`. Если подтверждения не будет, события
повторятся; в описании тула это сказано явно. **Первый запуск считается по источнику:** нет базы
источника → база создаётся без событий, статус `baseline`. Новый курс в `grades` и источник, упавший при
первом запуске, получают базу позже тем же правилом, поэтому ложных `added` нет.

### `hse_changes_reset({ scope?, confirm: true })`

Стирает базы и события области (или всего). Без `confirm: true` — отказ. `nextSeq` не сбрасывается;
`seen` ставится в `nextSeq − 1`.

### Ошибки записи

Ошибка записи на диск: события возвращаются, `persisted: false`, базы, `seen` и `nextSeq` не меняются,
следующий вызов вычислит то же самое. Тул не бросает исключений: отказ источника — статус в `sources`,
по образцу `digest`.

Описания тулов явно разводят `digest` («что есть») и `hse_changes` («что изменилось»).

## 11. Ложные события и частичные отказы

Источник → правила:

1. **Покрытие.** `lms_calendar`: ось — `due`; `from = today − 180 д`, `to = today + 60 д`; при
   `truncated` `to = max(due)` загруженного (усечение отрезает самые поздние события, граница плавает).
   `elk_schedule`: `from = today`, `to = today + 14 д`. `inbox`: `from = min(time)` выборки, если вернулось
   ровно `limit`, иначе без нижней границы. `added`/`removed` — только внутри пересечения покрытий; факты
   вне пересечения не порождают событий и сохраняются как есть, пока не окажутся в покрытии.
2. **Усечённый календарь** → `removed` по `lms_calendar` не вычисляется, `warnings`.
3. **Отказ источника** → база прежняя, событий нет, статус `error`; остальные источники коммитятся
   независимо. RUZ как замена ЕЛК-расписания **не используется** (другие `id` и формат — ложные
   события).
4. **Новые («`added`») во входящем** — только элементы свежее самого старого в старой выборке (внутри
   покрытия). Монотонность id у `local_mail` и уведомлений ЕЛК **не проверена**, на max id не полагаемся.
5. **Override-события Moodle** (свои id по пользователю/группе) могут выглядеть как `removed` + `added`;
   не проверено вживую.
6. **Идемпотентность.** Повторный вызов сразу после первого возвращает неподтверждённое (если `ack`
   не передан) либо пусто; новых страниц нет (кэш ≤ 60 с).

## 12. istudy, RUZ и известные ограничения

- **istudy вне №3.** По публичным источникам (пресс-релиз НИУ ВШЭ от 2026-09-28; копия на
  spb.hse.ru от 2026-09-29) система «ЯУчусь» переведена с 2026-09-29 на авторизацию через мессенджер
  MAX с двухфакторной аутентификацией. Что «ЯУчусь» — именно `istudy.hse.ru`, прямого источника нет:
  связь опирается на совпадение функций (зачётка, оценки, рейтинг); страница `istudy.hse.ru/auth` в
  поиске показывает вход «под учётной записью ВШЭ», дата слепка неизвестна. **Связь с дефектом F9 —
  гипотеза, не воспроизведена.** Разбор клиента (`istudy/client.ts:22–56`): ссылка с `/profile` →
  `goto` → ожидание ответов SPA → ошибка «не отдал ожидаемые данные»; такой результат дал бы и экран
  входа. Вход через MAX — отдельный будущий подпроект (интерактивное подтверждение на телефоне; хранить
  для него нечего и не нужно).
- **Оценки — только журнал LMS.** Итоговые и экзаменационные оценки из istudy не попадают.
- Точка расширения: источник — `{ id, scope, fetch → { facts, coverage, warnings } }`; когда появится
  рабочий способ входа, istudy добавляется одним извлекателем.
- **Риск:** если LMS/ЕЛК тоже перейдут на вход через MAX, `storage/hse-session.json` перестанет
  обновляться, все источники получат `error`. Дизайн к этому устойчив (база не трогается).
- **Единого вызова «оценки всех курсов» нет:** `gradereport_overview_get_course_grades` не помечена
  `ajax: true` и отдаёт только итоговые оценки (стандартный Moodle; кастомизация ВШЭ не проверялась).
  Оценки идут постраничным обходом курсов (§9).
- RUZ доступен только из сети ВШЭ и в снимках не используется.
- MCP-сервер живёт только пока открыт хост; фонового режима вне хоста нет. Это следствие решения
  «по запросу».

## 13. Безопасность и приватность

- Хранятся только нормализованные факты (§7), без токенов, `storageState`, email, ФИО отправителей
  и исполнителей, тел писем и текста заявок/уведомлений.
- Защита файла — ACL профиля (§7); `0o600` на Windows ничего не даёт.
- Записывающих операций нет; `hse_changes_reset` меняет только локальный файл и требует `confirm`.
- В логи и ответы токены, пароли и query-строки не попадают; скрипты проверки ничего не печатают.

## 14. Вне рамок

Записывающие действия (№4); удаление корпоративной почты (отдельная ветка и PR до №3); исправление
istudy и вход через MAX; фоновый процесс и таймеры; push-уведомления вовне; тесты и линтер (решение
проекта, `CLAUDE.md`).

**Долг перед №4 не чинится** (в №3 записей нет), но ревью уточнило его:
(а) `invalidates` с неизвестным именем бросает уже после успешной загрузки/записи
(`invalidateResource`, `resource.ts:121`), результат не кэшируется, вызывающий получает ошибку;
(б) `invalidates` с **известным** именем вызывает `clearCache` → `generation++`, и собственный
результат ресурса тоже не кэшируется (`cache.ts:61`); (в) для записывающих ресурсов нужен явный режим
«не кэшировать», а `maxAgeMs: 0` — не он. Имена из `invalidates` следует разрешать до загрузки.

## 15. Верификация

1. `npm run build` — без ошибок.
2. Изолированные скрипты через `dist/` (в репозиторий не коммитятся): нормализация и отпечаток
   (детерминизм, шум); `diff` (added/removed/changed/moved/overdue); покрытие и скользящее окно,
   `truncated`; ключ расписания и склейка в `moved`; первый запуск по источнику; частичный отказ;
   `nextSeq` и курсор после среза и reset; `ack` (повтор без ack, ack > issued); потолок 200 и `omitted`;
   срез журнала и `gap`; ошибка записи (`persisted:false`, без сдвига); атомарность, повреждённый JSON и
   `version` новее; lock-файл и устаревшая блокировка; `maxAgeMs` в кэше (попадание, промах, in-flight,
   поздняя загрузка не затирает свежую, `clearCache` не затронут); регрессия восьми функций без
   `opts`; `runTool` с `signal`; разбор `extractGradeTable` на фикстурах разметки Moodle.
3. Живая проверка на реальном аккаунте скриптом из scratchpad (`.env` читается в `process.env` без
   вывода, импорт из `dist/`; токены, пароли, ФИО, email, названия курсов, query-строки в вывод не
   попадают): создание баз по источникам; **повторный вызов — ноль событий и ноль новых страниц**; замер
   времени `grades` холодным и тёплым процессом; проверка гипотез из §16; проверка того, куда
   приходит `goto` istudy (только URL без query и признак экрана входа).
4. Diff на реальных данных проверяется **имитацией**: правка копии базы во временном каталоге и
   повторный снимок. Реального изменения на аккаунте вызвать нельзя (записей нет). В итоговой таблице
   помечается «имитация», а не «проверено вживую».
5. Итоги — отдельный раздел (§18) с разделением «проверено вживую / имитация / не проверено».
6. Документация: `docs/requirements.md` (новое функциональное требование; нефункциональное про
   хранимые данные), `CLAUDE.md` (архитектура `changes`, хранилище, `maxAgeMs`; описание istudy
   устарело — «причина отказа по публичным источникам, не воспроизведено»), `README.md` (тулы),
