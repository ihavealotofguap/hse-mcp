# Подпроект №2 «Сводки и планирование» — спецификация дизайна

Дата: 2026-10-14. Статус: черновик на ревью пользователя. База: ветка `worktree-update`,
коммит `e8bdc4c` (подпроект №1 «Надёжность и скорость» готов и проверен вживую).

## 1. Цель

Студент одним вызовом получает ответ на «что у меня сегодня», «что на неделе», «что горит» — без
ручного опроса десятка `elk_*`/`lms_*` тулов. Часть цели верхнего уровня «управлять учебной жизнью
полностью через MCP» (подпроект 2 из 4; №3 — проактивность, №4 — записывающие действия, в этот
подпроект не входят).

## 2. Решения (зафиксированы в диалоге)

| Вопрос | Решение |
|---|---|
| Состав «дедлайнов» | Задания LMS; тесты и прочие элементы LMS с датой закрытия; окна ЕЛК (период СОП, задачи, заявки); экзамены и зачёты |
| Формат вывода | Единый JSON: массив `items` одной схемы + объект `sources` со статусом каждого источника |
| Горизонт | Скользящие 7 дней. `my_deadlines` — параметр `days` (по умолчанию 14); просроченные включаются всегда |
| Состав `my_today` | Расписание, дедлайны, непрочитанная внутренняя почта LMS, непрочитанные уведомления ЕЛК, активные заявки и задачи ЕЛК |
| Корпоративная почта (IMAP, `mail_*`) | **Не входит ни в один агрегатор** — прямое решение пользователя |
| Курсы | По умолчанию только актуальные; необязательный фильтр `courses` |
| Источник расписания | ЕЛК основной; RUZ — только запасной, если ЕЛК-расписание не ответило (решение автора, без дублей занятий) |

## 3. Подходы

- **A. Сервис `digest`, вызывающий клиентские функции напрямую (выбран).** Единая схема элемента,
  `Promise.allSettled`, лимитер и кэш работают как есть.
- B. Агрегатор поверх MCP-тулов — лишний слой сериализации, хуже с частичными отказами. Отклонён.
- C. Один тул `my_overview({ scope })` — хуже для выбора тула моделью и для описаний. Отклонён.

## 4. Архитектура

Новый сервис `src/services/digest/` по образцу остальных (`client.ts` + `tools.ts`), плюс два
вспомогательных файла. Подключается в `src/index.ts` вызовом `registerDigestTools(server)`.

| Файл | Назначение | Зависимости |
|---|---|---|
| `types.ts` | `DigestItem`, `SourceStatus`, `DigestResult` | — |
| `sources.ts` | По одному коллектору на источник; каждый возвращает `DigestItem[]`; не знает про MCP | клиенты `elk`/`lms`/`ruz`, `date-utils.ts` |
| `client.ts` | `getToday()`, `getWeek()`, `getDeadlines({ days, courses })`: запуск коллекторов, слияние, сортировка, `sources` | `sources.ts` |
| `tools.ts` | `registerDigestTools(server)`: тулы `my_today`, `my_week`, `my_deadlines`, zod-схемы, `runTool()` | `client.ts`, `mcp-utils.ts` |

Агрегаторы вызывают **клиентские функции**, не MCP-тулы. Существующий код сервисов не меняется,
кроме возможного экспорта вспомогательной функции для календарного вызова Moodle (см. §6).

## 5. Модель данных

```ts
type ItemKind =
  | "lesson" | "exam"                       // расписание
  | "assignment" | "lms_activity"           // LMS: задания / тесты и прочее
  | "elk_window" | "elk_task" | "elk_claim" // ЕЛК: СОП и т.п. / задачи / заявки
  | "lms_message" | "notification";         // входящие

interface DigestItem {
  kind: ItemKind;
  when: string | null;      // ISO 8601 с локальным смещением; null — дата не распознана
  until?: string;           // конец (занятие, окно)
  title: string;
  course?: string;
  place?: string;           // аудитория/корпус для занятий
  source: string;           // имя коллектора, например "elk_schedule"
  overdue?: boolean;        // true только для элементов с датой в прошлом и без сдачи
  unread?: boolean;
  important?: boolean;      // isImportant уведомления ЕЛК
  url?: string;
  raw?: Record<string, unknown>; // нераспознанные поля (задачи ЕЛК, окна СОП)
}

interface SourceStatus { status: "ok" | "error" | "skipped"; error?: string; ms: number }

interface DigestResult {
  generatedAt: string;
  window: { from: string; to: string };
  items: DigestItem[];
  sources: Record<string, SourceStatus>;
}
```

Сортировка `items`: просроченные первыми (по `when` по возрастанию), затем по `when`, затем
элементы без даты. Время — в локальной зоне процесса (как в существующем `date-utils.ts`).

## 6. Тулы и их источники

| Тул | Параметры | Содержимое |
|---|---|---|
| `my_today` | — | Расписание на сегодня (`elk_schedule`); дедлайны (`lms_deadlines`, `elk_windows`, экзамены из расписания) — просроченные + до конца завтрашнего дня; непрочитанные письма LMS (`lms_messages`); уведомления ЕЛК с `isRead === false` (`elk_notifications`); заявки с `active === true` (`elk_claims`) и задачи ЕЛК (`elk_tasks`) |
| `my_week` | — | Расписание на 7 дней; дедлайны (`lms_deadlines`, `elk_windows`, экзамены) на 7 дней + просроченные. Без почты, уведомлений, заявок и задач (YAGNI; расширяется по запросу) |
| `my_deadlines` | `days?` (1–120, по умолчанию 14), `courses?` (массив id или подстрок названия) | `lms_deadlines`, `elk_windows`, `elk_tasks`, `elk_claims` (активные), экзамены/зачёты из расписания за `days`; просроченные всегда |

Коллекторы (`sources.ts`):

| Имя | Вызывает | Даёт |
|---|---|---|
| `elk_schedule` | `elk.getSchedule(from, to)` | `lesson`/`exam`. Экзамен — `lesson_type` совпал с `/экзамен\|зач[её]т\|коллоквиум/i`. Время: `day.date` + `begin_time`/`end_time` |
| `ruz_schedule` | `ruz.getStudentInfo(config.hseEmail)` → `ruz.getSchedule` | Только если `elk_schedule` завершился ошибкой; в остальных случаях `status: "skipped"`. Не кэшируется |
| `lms_deadlines` | см. §7 | `assignment` / `lms_activity` |
| `lms_messages` | `lms.listMessages(50)` | `lms_message`, только `unread === true` |
| `elk_notifications` | `elk.getNotifications(50)` | `notification`, только `isRead === false` |
| `elk_claims` | `elk.listRequests()` | `elk_claim`, только `active === true` |
| `elk_tasks` | `elk.listTasks()` | `elk_task`; форма задачи на реальных данных не подтверждена (на проверенном аккаунте их нет) — поля кладутся в `raw`, `title` берётся из первого распознанного текстового поля (`title`/`name`/`text`), иначе «Задача ЕЛК» |
| `elk_windows` | `elk.getCourseEvaluationStatus()` | `elk_window`: каждая строка с `when`, если в ней распознана дата; иначе `when: null` и строка целиком в `raw`. Фильтрация «активных» по тексту статуса уточняется по реальной форме строк при реализации; без однозначного признака строка включается |

Реализация `my_today`/`my_week`/`my_deadlines` — выбор подмножества коллекторов и окна дат; общей
логики слияния нет в тулах (она в `client.ts`).

## 7. Источник дедлайнов LMS

Интерфейс один: `listLmsDeadlines({ from, to, includeOverdue, courses }) → DigestItem[]`. Реализаций
две, выбор между ними делается в начале реализации **живым зондированием** по заданному правилу:

1. **Основная — календарь Moodle одним AJAX-запросом.** Пробуется
   `core_calendar_get_action_events_by_timesort` через существующий `fetchMoodleAjax` (авторизация
   по sesskey, как у `lms_list_courses`/`lms_list_messages`). Если сессия получает ответ без
   `error` и события содержат таймстампы и признак «требует действия» — это путь по умолчанию:
   даёт все курсы за один вызов, без обхода страниц и без разбора русских дат.
2. **Запасная — по странице на курс.** Если п.1 недоступен: для каждого курса из выборки (§8)
   вызывается `lms.listAssignments(courseId)`; из строк `table.generaltable` разбираются дата
   сдачи (русские форматы) и статус сдачи. Строка без распознанной даты остаётся с `when: null`,
   не отбрасывается. Курс в `course` проставляет агрегатор (в строках таблицы его нет).

Общее для обеих реализаций: таймаут коллектора 20 с (зависание не блокирует остальные источники);
результат кэшируется ключом `lms:deadlines:<хэш окна и курсов>` с TTL `TTL.medium` — префикс
`lms:` означает, что `hse_clear_cache` его сбрасывает.

## 8. Выбор курсов

`lms.listCourses()` → оставить курсы с `visible === true`, `hidden === false` и (`enddate === null`
либо `enddate` ≥ сегодня). Параметр `courses` сужает выборку: число — точный `id`, строка —
регистронезависимая подстрока `fullname`/`shortname`. Если фильтр не нашёл ни одного курса, это
ошибка источника `lms_deadlines` с перечнем доступных названий, а не пустой результат. Фильтр
относится только к LMS-источникам; расписание и ЕЛК им не ограничиваются.

## 9. Ошибки и частичные отказы

- Все коллекторы запускаются через `Promise.allSettled`; падение одного даёт
  `sources[<имя>] = { status: "error", error, ms }`, остальные элементы возвращаются.
- Агрегат сам по себе не кэшируется: он состоит из кэшируемых частей (`elk:`/`lms:`), а RUZ в
  требованиях не кэшируется.
- RUZ вызывается только как запасной (ошибка `elk_schedule`), чтобы вне кампуса не платить
  таймаутом/редиректом за заведомо недоступный источник.
- Корпоративная почта не вызывается вовсе; параметр `HSE_MAIL_APP_PASSWORD` агрегаторам не нужен.
- Если упали все источники, тул всё равно возвращает `DigestResult` с пустым `items` и ошибками в
  `sources`, а не бросает исключение.

## 10. Нагрузка и ограничения платформы

- Каждый вызов клиентской функции держит максимум одну страницу; лимитер (3 одновременных,
  ≥300 мс между открытиями) работает внутри `openAuthenticatedPage`. Агрегатор не открывает страницы
  сам и не обходит лимитер.
- Холодный запасной путь на ~17 курсах оценочно занимает несколько секунд (17 × ~0,6 с / 3 +
  паузы), повторный вызов — из кэша. Это оценка, реальное время фиксируется живым замером.
- Записывающих операций нет; новые тулы только читают.

## 12. Верификация

1. `npm run build` — без ошибок.
2. Изолированные скрипты через `dist/`: разбор русских дат; сортировка и слияние; статусы при
   подмене упавшего коллектора; фильтр курсов; определение экзамена по `lesson_type`.
3. Живая проверка на реальном аккаунте скриптом из scratchpad: читает нужные ключи из
   `C:\Users\alexk\hsemcp\.env` в `process.env` без вывода, импортирует `dist/`; токены, пароли,
   ФИО и email в вывод не попадают. Замеряется время холодного и повторного вызова каждого тула.
   Заодно проверяются `lms_*`/`istudy_*` через кэш (закрывает пункт «не проверено» подпроекта №1).
4. Остаются «не проверено», пока нет безопасного способа воспроизвести: сквозной повтор при реально
   протухшем токене ЕЛК, протухшая SSO-сессия Keycloak, форма записи задачи ЕЛК, поведение RUZ из
   сети ВШЭ.
5. Документация: `PROGRESS.md` (раздел «Подпроект 2», честное разделение «проверено вживую» /
   «не проверено»), `REQUIREMENTS.md` (новое функциональное требование + нефункциональное про
   частичные отказы), `CLAUDE.md` (архитектура: сервис `digest`), `README.md` (список тулов).

## 13. Открытые вопросы реализации (решаются живым зондированием, не пользователем)

- Работает ли календарный AJAX-метод Moodle на `edu.hse.ru` (§7, п.1); от этого зависит, какая
  из двух реализаций станет основной.
- Формат `begin_time`/`end_time`/`date` в ответе `get-myschedule` (одно поле даты-времени или
  отдельные дата и `HH:MM`) — определяет сборку ISO в `elk_schedule`.
- Форма строк `getCourseEvaluationStatus` — как выделить дату окна и признак «активно».
