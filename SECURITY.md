# Безопасность

## Как сообщить об уязвимости

Не публикуйте подробности в открытом issue. Используйте приватное сообщение об уязвимости на GitHub
(вкладка Security репозитория, «Report a vulnerability»). Если оно недоступно, откройте issue без
технических деталей и попросите связаться в приватном порядке. В сообщении не присылайте свои пароли,
файлы `storage/` и содержимое `.env`.

## Что считается секретом

- пароль учётной записи ВШЭ (системное хранилище, `.env` или переменная окружения `HSE_PASSWORD`);
- `storage/hse-session.json` — куки и токены сессии, не менее чувствительны, чем пароль;
- `storage/writes/key` — ключ подписи токенов предпросмотра записи;
- содержимое `storage/` целиком: журналы, снимки изменений, папка «исходящих».

`.env` и `storage/` находятся в `.gitignore`. Не добавляйте их в коммиты, скриншоты и сообщения об ошибках.

## Как проект хранит секреты

1. Пароль берётся по порядку: переменная окружения процесса `HSE_PASSWORD`, системное хранилище
   (Windows Credential Manager, macOS Keychain, Linux Secret Service; служба `hsemcp`, учётная запись —
   `HSE_EMAIL`), `.env` как запасной путь. Заводится командой `npm run credentials:set`.
2. Файлы `storage/hse-session.json` и `storage/writes/key` создаются с правами `0o600` (POSIX); на Windows
   права ограничиваются владельцем через `icacls` (best-effort, ошибки не выводятся).
3. Пароль, куки и токены не попадают в ошибки, stderr и ответы тулов. При чтении пароля из `.env`
   сервер пишет в stderr одно предупреждение без значения.

Проект не использует собственное шифрование: ключ рядом с данными давал бы только иллюзию защиты.

## Модель угроз

Защита рассчитана на случайную утечку (коммит, скриншот, лог, публикация репозитория) и на чтение файлов
другим пользователем той же системы. От вредоносной программы под тем же пользователем она не защищает:
пароль вводится в форму входа ВШЭ и находится в памяти процесса.

## Что делать при утечке

1. Смените пароль учётной записи ВШЭ.
2. Удалите каталог `storage/` (сессия и ключ создадутся заново).
3. Выполните `npm run credentials:clear`, затем при необходимости заново `npm run credentials:set`.
4. Если секрет попал в коммит или в публичный репозиторий, считайте его раскрытым: смена пароля обязательна,
   удаление коммита её не заменяет.

## Рекомендации для репозитория

Включите на GitHub secret scanning и push protection. По желанию добавьте `gitleaks` в pre-commit-хук
(в зависимости проекта он не входит).
